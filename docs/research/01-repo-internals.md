## Question

What makes a multi-language repository (TypeScript, Rust, C under ESP-IDF, WebAssembly) navigable and safe for AI agents to work in, and which tools enforce that automatically? Specifically: (1) how projects structure and maintain `AGENTS.md`/`CLAUDE.md` files, including kari-website's recorded history; (2) how specs, plans and ADRs are stored so agents implement from them, with template fields and any claimed effect on fidelity; (3) what architecture-enforcement tooling exists per language at current versions, what each checks and cannot check, and how JSON Schema drift is caught in CI; (4) what harness vendors publish about codebase properties that help their agents; (5) whether any multi-language monorepo maintained mostly by agents exists publicly and what it recorded going wrong.

## Findings

### 1. Agent guidance files

1. **The AGENTS.md spec prescribes no structure.** "AGENTS.md is just standard Markdown. Use any headings you like." Nested files: "the closest AGENTS.md to the edited file wins; explicit user chat prompts override everything." The site claims 60,000+ projects use it, lists Claude, Codex, Jules, Cursor, Copilot, Aider and others as readers, and is "stewarded by the Agentic AI Foundation under the Linux Foundation". No versioning. (https://agents.md/) [verified]

2. **Codex caps combined instruction files at 32 KiB by default** (`project_doc_max_bytes`), concatenates files from the Git root down to the cwd ("Files closer to your current directory override earlier guidance because they appear later in the combined prompt"), stops adding files once the cap is hit, and supports `AGENTS.override.md` and configurable fallback filenames. (https://learn.chatgpt.com/docs/agent-configuration/agents-md) [verified]

3. **Codex's own content guidance is "short and accurate", with a defined update trigger.** "A short, accurate AGENTS.md is more useful than a long file full of vague rules." Recommended contents: repo layout, how to run, build/test/lint commands, conventions and PR expectations, do-not rules, "What done means and how to verify work." Maintenance: "When Codex makes the same mistake twice, ask it for a retrospective and update AGENTS.md." When it grows: "keep the main file concise and reference task-specific markdown files for things like planning, code review, or architecture." (https://learn.chatgpt.com/guides/best-practices) [verified]

4. **Claude Code sets a numeric size target and says imports do not reduce cost.** "Size: target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." "Imports help you organize a long file but don't reduce its context cost, because imported files also load at launch." Path-scoped `.claude/rules/*.md` with `paths:` frontmatter load only when matching files are touched; subdirectory CLAUDE.md files load on demand when Claude reads files there. (https://code.claude.com/docs/en/memory) [verified]

5. **Claude Code states guidance files are advisory and names the deterministic alternative.** "Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead." The best-practices page repeats it: "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic." (https://code.claude.com/docs/en/memory; https://code.claude.com/docs/en/best-practices) [verified]

6. **Claude Code's pruning rule and include/exclude table.** "For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it. Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" Include: commands Claude can't guess, style rules that differ from defaults, test instructions, repo etiquette, project-specific architectural decisions, env quirks, gotchas. Exclude: anything derivable from code, standard conventions, detailed API docs, frequently changing info, tutorials, file-by-file descriptions. "Treat CLAUDE.md like code: review it when things go wrong, prune it regularly, and test changes by observing whether Claude's behavior actually shifts." `/doctor` proposes cuts; `/doctor prompt-audit` audits CLAUDE.md, AGENTS.md, rules, skills, subagents for conflicts. (https://code.claude.com/docs/en/best-practices; https://code.claude.com/docs/en/memory) [verified]

7. **Claude Code reads AGENTS.md natively since v2.1.277**, only when no CLAUDE.md/CLAUDE.local.md exists in or above the cwd (default `claude-md-or-agents-md`; `claude-md-and-agents-md` loads both). A `CLAUDE.md` containing `@AGENTS.md` is the documented portable fallback for sessions that cannot load AGENTS.md directly (pre-2.1.281 Bedrock/telemetry-off sessions). (https://code.claude.com/docs/en/memory) [verified]

8. **Gemini CLI and Jules.** Gemini CLI loads `GEMINI.md` hierarchically (global, workspace, and just-in-time from directories touched by tools), supports `@file.md` imports, and can be told to read `AGENTS.md` via `context.fileName: ["AGENTS.md", ...]`; no size guidance. Jules reads `AGENTS.md` from the repo root and says only "Keep AGENTS.md up to date. It helps Jules and your teammates work with your repo more effectively"; it also "refer[s] to agents.md or your readme.md file for hints to setup an environment on the fly". (https://geminicli.com/docs/cli/gemini-md/; https://jules.google/docs/; https://jules.google/docs/environment/) [verified]

AGENT-SKILL-START/END` YAML blocks of type `agents-md-commands` from `contributing-docs/*.rst` and rewrites the region between `<!-- START generated-commands ... -->` and `<!-- END generated-commands ... -->` in AGENTS.md. `check-documented-commands` ("Check documented breeze and prek commands exist") validates every `breeze ...` and `prek run <hook-id>` mentioned in AGENTS.md and the docs tree against the CLI's actual click tree and hook ids; its docstring cites two real drift incidents (apache/airflow#69861 documented a command that never existed; #43979 renamed a command and left a stale doc line) and states a precision-over-recall policy ("a checker that cries wolf gets SKIPped"). (apache/airflow `.pre-commit-config.yaml` lines ~170-198 and ~1158-1176; `scripts/ci/prek/generate_agent_skills.py`; `scripts/ci/prek/check_documented_commands.py`) [verified]

12. **Zed encodes a maintenance policy inside the file itself ("Rules Hygiene").** Agents must not edit rules inline; they add a "Suggested .rules additions" heading to the PR description and "Reviewers decide what gets merged." New rules must be non-obvious, repeatedly encountered, and specific enough to act on; crate-specific rules go in that crate's own `.rules`. "Avoid architectural descriptions of a crate (module layout, data flow, key types). These go stale fast and the agent can gather them by reading the code. Rules should be traps to avoid, not maps to follow." Rules are added in "A dedicated commit ... with context on why it exists." (zed-industries/zed `AGENTS.md`, section "Rules Hygiene") [verified]

### 2. Specs and plans as repository artifacts

22. **superpowers 6.4.1 `brainstorming` classifies work into three paths and gates implementation behind approval of a written spec for architectural work.** Spec path: `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`, committed. The design must "Cover: architecture, components, data flow, error handling, testing". Spec self-review: placeholder scan, internal consistency, scope check ("focused enough for a single implementation plan"), ambiguity check ("Could any requirement be interpreted two different ways? If so, pick one"). Design principle stated to the agent: "you reason better about code you can hold in context at once, and your edits are more reliable when files are focused. When a file grows large, that's often a signal that it's doing too much." No measured fidelity claim; rationale only. (`.../superpowers/6.4.1/skills/brainstorming/SKILL.md`) [verified]

23. **superpowers 6.4.1 `writing-plans` fixes a plan template.** Header fields: Goal (one sentence), Architecture (2-3 sentences), Tech Stack, Spec (path; "the plan argues from the spec, so the spec travels with it"), Global Constraints ("exact values copied verbatim from the spec"), Review Focus (the five input classes "the spec implies but no task's tests exercise", each pinned to a test in the owning task). Per task: Files (Create / Modify with `path:123-145` line ranges / Test), Interfaces (Consumes / Produces with exact signatures, because "A task's implementer sees only their own task"), then five TDD steps with exact commands and expected output. "No Placeholders" bans "TBD", "add validation", "Similar to Task N", and references to undefined types. Self-review: spec coverage, placeholder scan, type consistency across tasks, review-focus coverage. Plans save to `docs/superpowers/plans/YYYY-MM-DD-<feature>.md`. Rationale for file structure: "Prefer smaller, focused files over large ones ... Files that change together should live together. Split by responsibility, not by technical layer." No measured fidelity claims. (`.../superpowers/6.4.1/skills/writing-plans/SKILL.md`) [verified]

## What others do

- **Short map, deep docs.** The large, mature files point outward: Airflow (12 links), next.js (11), Biome (9, into skills), ruff (7), kari (8 trigger lines into `docs/`). OpenAI's internal repo made the map ~100 lines with `docs/` as system of record. Codex and Claude Code docs both say to keep the root file short and move specifics into referenced files or on-demand rules. (Findings 3, 4, 9, 11, 13, 18, 21, 29)
- **Numeric budgets differ by vendor and are all exceeded by some popular repos.** Anthropic: under 200 lines; OpenAI (internal): ~100 lines; Codex (tool): 32 KiB hard cap on the concatenation. Airflow and next.js sit at 250 and 520 lines. (Findings 2, 4, 9, 21)
- **"Traps, not maps."** Zed, Claude Code docs and Codex docs all say not to describe what the agent can read from code; include non-obvious, repeatedly-hit rules. Zed and Codex both tie additions to repeated mistakes. (Findings 3, 6, 12)
- **Guidance is advisory; enforcement is a separate mechanism.** Anthropic says so explicitly (hooks); Airflow validates its AGENTS.md commands against the real CLI; claude-code's CLAUDE.md names the CI check behind its rules; opencode and pi name guards behind specific rules. Everywhere else, including kari-website, nothing checks the file. (Findings 5, 11, 14, 15, 16, 19)
- **Harness-neutral file, harness-specific shim.** ruff and kari use `CLAUDE.md` = `@AGENTS.md`; Zed keeps identical copies; Claude Code now reads AGENTS.md natively; Gemini CLI can be configured to. (Findings 7, 8, 9, 20)
- **Nested per-area files are common and small.** ghostty, kari (`api/`), openai/codex (`codex-rs/tui/.../bottom_pane`), Airflow (`task-sdk/.../_shared`), opencode (`src/session/llm`). Zed's rule: crate-specific rules go in the crate's own file. (Findings 9, 10, 11, 12)
- **Specs are directories or dated files with numbered, testable requirements and file-level task scope.** spec-kit: `specs/NNN-feature/{spec,plan,tasks}.md` with FR-/SC- ids and `[P]`/`[US1]` task tags; Kiro: `.kiro/specs/<name>/{requirements,design,tasks}.md`; superpowers: dated `docs/superpowers/{specs,plans}/` with Files/Interfaces per task; OpenAI: `docs/{design-docs,exec-plans,product-specs}`. All demand "out of scope" and an end-to-end verification. None publishes fidelity measurements. (Findings 22-27, 29, 31, 32)
- **Generated artifacts are regenerated in CI and either fail the build (ruff) or get auto-committed (Biome); humans and agents are told never to hand-edit them.** (Findings 15, 48)
- **Per-language enforcement stacks are layered: a graph/boundary tool, a dead-code tool, a dependency-policy tool, a style linter.** TS: dependency-cruiser or eslint-plugin-boundaries + knip + Biome/ESLint. Rust: workspace lints + clippy + cargo-deny + cargo-machete/udeps. C/IDF: clang-tidy via esp-clang (still "under development") + IWYU + kconfcheck + component REQUIRES. No single tool spans languages. (Findings 33-46)
- **Vendors converge on verification and context economy; only OpenAI's internal write-up prescribes structural tests on code (dependency direction, file size, naming).** (Findings 49-53)
