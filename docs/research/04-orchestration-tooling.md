## Question

kari-website built its agent fleet by hand: a systemd user timer calling a
bash dispatcher every 15 minutes, agent definitions as Markdown with YAML
frontmatter, headless `claude -p` sessions, per-agent locks, a Telegram
long-poller, per-run usage records, a one-shot fallback-model retry on quota
errors, and an orchestrator prompt that enforces a worker cap, model tiering,
worktree isolation and a `needs-human` protocol. This file lists every
capability that system provides (as a checklist), then records what existing
tools and services provide today across five areas (harness-native scheduling
and cloud agents, GitHub-native orchestration, open-source orchestrators and
issue resolvers, general workflow engines, human chat channels), and closes
with a fit table against panelator's settled principles: pull-on-completion
scheduling into a concurrency slot, bot-authored issue authority enforced in
script, model tiering by stage, cost caps, agents on the maintainer's laptop,
Telegram as the human channel. The build / adopt / adopt-and-extend decision is
left to the thinking run.

## Findings

### A. The kari-website capability checklist

Each capability is tagged **[script]** when a shell script enforces it and
**[prompt]** when only an agent prompt asks for it. The distinction matters
because process-spec section 4.3 requires script enforcement.

1. **Periodic tick.** A systemd user timer fires `dispatch.sh` on a 15-minute grid (`OnCalendar=*:00/15`, `Persistent=false`, so slots missed while asleep are not replayed). `automation/systemd/kari-automation.timer`; README lines 276-318. [verified] [script]
2. **Per-agent interval with drift control.** Each agent declares `every: Nm|Nh|Nd`; an agent is due once `now - last >= every - tolerance` with a 120 s default tolerance, stamped at run start so long runs do not re-trigger. `dispatch.sh` lines 119-144, 337-347, 864-894; README 380-406. [verified] [script]
3. **Agent definition format.** One Markdown file per agent, YAML frontmatter (`name`, `enabled`, `every`, `model`, `fallback`) plus the prompt body; adding an agent is one commit with no dispatcher change. README 76-96; `dispatch.sh` 318-335 (frontmatter parser). [verified] [script]
4. **Headless harness invocation.** `claude -p --dangerously-skip-permissions --output-format json [--model] [--fallback-model]`, prompt on stdin, run from the repo root so CLAUDE.md loads, with `CI=true` and `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=5400000` (90 min) in the environment. `dispatch.sh` lines 81-99, 697-715. [verified] [script]
5. **Per-agent mutual exclusion.** A `flock -n` on `<name>.lock` so an agent never overlaps itself; a held lock makes the tick skip. `dispatch.sh` 597-601, 747. [verified] [script]
6. **Worker concurrency cap.** `MAX_IN_FLIGHT = 1` lives in the orchestrator prompt's Budget section and is counted by the orchestrator over `agent/*` branches; the README says it is "a usage budget, not a coordination limit". `agents/issue-pipeline.md` lines 17-24, 64-70; README 489-523. [verified] [prompt]
7. **Per-run usage accounting.** The session's JSON result object (`total_cost_usd`, `num_turns`, `duration_ms`, `usage`, per-model `modelUsage`) is folded into the log as `usage:` lines and kept raw under `usage/<name>-<stamp>.json` for 180 days; `--status` sums runs, total and mean cost. `dispatch.sh` 365-440, 903-907; README 132-164. [verified] [script]
8. **Fallback on capacity vs. fallback on quota.** `--fallback-model` handles overload mid-session; separately the dispatcher retries the whole tick once on the fallback model only when the result object has `api_error_status == 429` and the failed attempt cost at most `KARI_AUTOMATION_RETRY_COST_LIMIT` (default $2). `dispatch.sh` 561-589, 727-744; README 554-589. [verified] [script]
9. **Model tiering by stage.** "judgment gets fable, implementation gets opus": validation, plan and review subagents on the stronger tier; worker and fix agents on the cheaper one; stronger-tier work is postponed, never downgraded, on a usage limit. `agents/issue-pipeline.md` lines 787-815; design spec Decisions log ("Model split"). [verified] [prompt]
10. **Telegram transport.** `telegram.sh poll` is called at the top of every tick (long polling via `getUpdates`, offset file in the state dir); `telegram.sh send <text> --issue N` remembers the message id so a reply routes to that issue; replies are posted to GitHub *before* anything else and remove `needs-human`/`blocked`; `/pause`, `/resume`, `/status` are understood; a reply drops a `nudge` file that makes the next tick treat every agent as due. README 173-245; `telegram.sh` header lines 1-45; `dispatch.sh` 799-801, 837-841. [verified] [script]
11. **Mechanical alerts.** Three alert conditions (`usage-limit`, `tick-failed`, `lock-<agent>`) each rate-limited to one message per 4 h, with a baseline-only first scan. `dispatch.sh` 442-559. [verified] [script]
12. **Pause.** `automation/PAUSE` file (also toggled by Telegram) or `enabled: false`. README 165-171; `dispatch.sh` 803-821. [verified] [script]
13. **Self-update of the clone.** Each real tick runs `git fetch` and `merge --ff-only origin/main`, only on `main`, warning and continuing on failure; introduced after a cadence cut sat inert for 17 hours (#399). `dispatch.sh` 766-789. [verified] [script]
14. **Process containment on the laptop.** Each session runs in a transient `systemd-run --user --scope` with `OOMPolicy=continue` and `MemoryMax=50%`, leftover processes are reaped when `claude` exits (#401, #412), and the tick holds a `systemd-inhibit --what=sleep:idle` lock (2026-08-19 suspend incident). `dispatch.sh` 621-677, 721-726; README 319-349, 408-428. [verified] [script]
15. **Run-log trailer.** Every log ends in `tick exited <code>` from an EXIT trap so a killed tick is distinguishable from a running one; logs pruned after 30 days. `dispatch.sh` 358-363, 616-617, 903. [verified] [script]
16. **Deterministic shortlist feed.** `backlog-shortlist.sh` paginates the whole open backlog through the REST API ("no `--limit` truncation, no lagging search index"), filters claimed/blocked issues, prints bounded JSON slices (`priority`, `user_feedback`, `bugs`, `maintainer`, `product`, `tooling`) with `*_omitted` counts, ranked by `unblocks` then age. `backlog-shortlist.sh` lines 1-40; README 43-59. [verified] [script]
17. **Stale-claim liveness probe.** `claim-liveness.sh <slug> [issues]` prints read-only facts (open PR, worktree mtimes, branch tips, issue activity, live `claude` process) and a `verdict=ALIVE|DEAD`; a failing probe counts as life. `claim-liveness.sh` lines 1-30; README 60-68, 525-552. [verified] [script, consumed by prompt]
18. **PR ownership by two independent signals.** `agent/*` branch prefix AND `agent-pr` label; disagreement means never merge. README 111-130; `agents/issue-pipeline.md` 48-52. [verified] [prompt]
19. **Worktree isolation per issue.** All code work in sibling worktrees `../kari-website-<slug>`; never `git checkout` in the main clone. `agents/issue-pipeline.md` 53-56, 818-821. [verified] [prompt]
20. **Human escalation protocol.** Record the ask on GitHub first (`needs-human` label, `Blocks: #N` line), then `telegram.sh send ... --issue`, then continue the tick; only the orchestrator sends; informational notes stay out of the channel. `agents/issue-pipeline.md` 77-118. [verified] [prompt + script]
21. **Brief templates per role.** `templates/validation-brief.md`, `plan-brief.md`, `worker-brief.md`, `fix-brief.md`, `review-brief.md` with `{{PLACEHOLDER}}` slots filled by the orchestrator. README 40-42; `templates/` listing. [verified] [prompt]
22. **Fix-cycle escalation valve.** If the same review feedback survives two consecutive fix cycles, dispatch a plan agent against the diff; if that fails, leave the PR for a human. `agents/issue-pipeline.md` 800-808. [verified] [prompt]
23. **Stateless orchestrator, state in GitHub.** "trust only what GitHub shows you now, never assumptions about previous ticks". `agents/issue-pipeline.md` 8-15; design spec Decisions log ("stateless, crash-proof, survives reboots"). [verified] [prompt]
24. **Serial squash merge.** `agents/issue-pipeline.md` 71-72. [verified] [prompt]
25. **WIP rescue.** On claim release, uncommitted work is saved to `wip/<slug>-<stamp>.patch` and a branch ahead of `main` is pushed and kept; the next worker is handed the material. README 541-552. [verified] [prompt]
26. **Diagnostics and tests.** `--dry-run` emits a stable tab-separated decision per agent; `--status`/`--status-brief` report last run, next due, lock, gaps, cost; `dispatch-test.sh`, `telegram-test.sh`, `backlog-shortlist-test.sh`, `install-timer-test.sh` run in CI. README 247-274, 69-74. [verified] [script]
27. **Design rationale recorded.** The 2026-08-19 design spec chose "local cron + headless sessions (chosen over a long-running /loop session and manual kick-off) — stateless, crash-proof, survives reboots" and accepted `--dangerously-skip-permissions` as a deliberate risk ("the playbook is the constraint"). `docs/superpowers/specs/2026-08-19-automation-fleet-design.md`, Decisions log and Architecture sections. [verified]

### B. Harness-native scheduling and cloud agents

**Claude Code**

28. Claude Code offers three scheduling surfaces with a documented comparison table: cloud **Routines** (runs on Anthropic-managed cloud, machine may be off, "No (fresh clone)" local file access, no permission prompts, minimum interval 1 hour), **Desktop scheduled tasks** (your machine, app must be open and awake, local files, minimum 1 minute), and in-session **`/loop`** (requires an open session, 7-day expiry). https://code.claude.com/docs/en/scheduled-tasks ("Compare scheduling options"). [verified]
29. Routines are "in research preview" and have three trigger types: schedule, an HTTP `POST .../routines/<id>/fire` endpoint with a per-routine bearer token (beta header `experimental-cc-routine-2026-04-01`), and GitHub events limited to **pull request** and **release** categories with filters (author, title, labels, branches, draft, merged). There is no issue event trigger. https://code.claude.com/docs/en/routines ("Supported events"). [verified]
30. Routines run "on Anthropic-managed cloud infrastructure, or on your organization's self-hosted environment when routed there"; self-hosted environments are a Team/Enterprise feature (`claude self-hosted-runner`, CLI reference). Routines are per individual claude.ai account, draw down subscription usage "the same way interactive sessions do", and commits/PRs "carry your GitHub user". Hourly caps: 100 scheduled runs/account, 30 Run-now+API fires per routine, 100 API fires/account; GitHub webhook events have undocumented "per-routine and per-account hourly caps" and "Events beyond the limit are dropped". https://code.claude.com/docs/en/routines ("Usage and limits", "Create a routine"). [verified]
31. Routines are available on Pro, Max, Team and Enterprise; `/schedule` requires a claude.ai subscription login and is unavailable with a Console API key or Bedrock/Vertex/Foundry. Model is selected per routine ("The prompt input includes a model selector"). API-trigger `text` arrives wrapped in a `<routine-fire-payload>` block labelled untrusted. https://code.claude.com/docs/en/routines. [verified]
32. Desktop scheduled tasks run "only while the app is open and your computer is awake"; a missed window yields "exactly one catch-up run for the most recently missed time"; a skipped-run reason includes "the previous run was still in progress, or other scheduled tasks were already running"; each task has its own permission mode and an optional isolated worktree; the prompt lives at `~/.claude/scheduled-tasks/<task>/SKILL.md` with YAML frontmatter. https://code.claude.com/docs/en/desktop-scheduled-tasks. [verified]
33. Cloud sessions can be created from the CLI (`claude --cloud "task"`), steered with `claude -p "msg" --cloud <session-id>` (JSON output `{ok, session_id, url}`), and pulled back with `--teleport`; "There is no separate compute charge for the cloud VM" and sessions "share rate limits with all other Claude and Claude Code usage within your account". Cloud session **auto-fix** subscribes to PR CI failures and review comments. https://code.claude.com/docs/en/claude-code-on-the-web. [verified]
34. Headless `claude -p` emits `total_cost_usd` and per-model `modelUsage` with `--output-format json`, supports `--max-turns`, `--max-budget-usd` (print mode only; subagent spend counts), `--fallback-model` (comma-separated chain, "when the primary model is overloaded or not available"), `--resume <id>` and `--continue`, `--permission-prompts none`, `--bare`, and exits 143 on SIGTERM. Background subagents are waited for up to `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` (default 10 minutes), which is the exact mechanism kari-website overrode (finding 4). https://code.claude.com/docs/en/headless; https://code.claude.com/docs/en/cli-reference. [verified]
35. Cost fields are "client-side estimates, not authoritative billing data"; `usage` excludes subagent tokens while `total_cost_usd` and `modelUsage` include them; a resumed session's result "report[s] the session's whole total, earlier runs' spend included" from v2.1.277. https://code.claude.com/docs/en/agent-sdk/cost-tracking. [verified]
36. Sessions are persisted at `~/.claude/projects/<encoded-cwd>/*.jsonl`; `resume` works from any directory on the same machine (v2.1.223+); cross-host resume needs a `SessionStore` adapter or moving the file. https://code.claude.com/docs/en/agent-sdk/sessions ("Resume across hosts"). [verified]

**OpenAI Codex**

37. Codex cloud tasks "can keep working while your computer is asleep", are started from the ChatGPT UI, the CLI, GitHub `@codex` mentions, or scheduled automations; internet access and "Network secrets" are per-environment toggles. The page documents no external API for starting a cloud task from one's own runner. https://learn.chatgpt.com/docs/cloud. [verified]
38. Codex automations are two kinds: "Scheduled Tasks create a new thread every time they run, while Scheduled Messages use the same existing thread"; schedules use RFC 5545 RRULE including minute-based intervals; on web/mobile "eligible plans can also run tasks from supported app events"; desktop-app project-scoped tasks "keep the machine powered on and the ChatGPT desktop app running"; creation is conversational or via the Scheduled sidebar, and "The Codex CLI doesn't provide the Scheduled management interface". https://learn.chatgpt.com/docs/automations.md?surface=app. [verified]
39. In GitHub, `@codex review` and `@codex security review` post reviews; "Other @codex mentions: Start a legacy cloud chat using the pull request as context"; a mention on an issue "spins up a cloud task ... and opens a draft pull request" (the issue-mention claim comes from the search summary of the same doc family and is not quoted from the fetched page). Automatic review requires enabling per repository with push/admin permission. https://learn.chatgpt.com/docs/third-party/github. [verified for PR mentions; issue-mention behaviour unverified]
40. Codex is "included in your ChatGPT Free, Go, Plus, Pro, Business, Edu, or Enterprise plan"; "Local messages and cloud chats share your plan's usage allowance. Weekly limits may also apply"; extra usage is bought as credits per million tokens; local chats can alternatively run on an API key "at standard API rates". https://learn.chatgpt.com/docs/pricing. [verified]
41. `openai/codex-action` installs the Codex CLI on the runner with a "secure proxy to the Responses API", takes `prompt`/`prompt-file`, `model`, `effort`, `codex-args`, `output-schema(-file)`, `safety-strategy` (`drop-sudo` default, `unprivileged-user`, `read-only`, `unsafe`), `permission-profile`, `allow-users`/`allow-bots`; it "doesn't directly create PRs or push code" (a following job does), runs on self-hosted Linux/macOS runners, and documents no cost output. https://github.com/openai/codex-action. [verified]

**GitHub Copilot cloud agent**

42. Copilot cloud agent is triggered by assigning an issue to Copilot, `@copilot` on a PR, the agents panel, external integrations (Teams, Slack, Azure Boards, Jira, Linear), and automations; it "runs ... in its own ephemeral development environment, powered by GitHub Actions", can open "exactly one pull request" per task, has a "59 minutes" maximum, and cannot bypass rulesets unless added as a bypass actor. https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent. [verified]
43. Automations (changelog 2026-06-02) run the cloud agent "on a schedule or in response to repository events": hourly/daily/weekly, issue opened, PR opened, PR synchronized; "Token usage is billed to the user who created the automation at standard usage-based rates"; sessions "will be visible to everyone with read access to the repository"; at launch "available for private and internal repositories, with public repository support coming soon". https://github.blog/changelog/2026-06-02-schedule-and-automate-tasks-with-copilot-cloud-agent/; https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/create-automations. [verified]
44. The agent can be driven programmatically: REST `"assignees": ["copilot-swe-agent[bot]"]` on create/update/add-assignees, or GraphQL mutations with header `GraphQL-Features: issues_copilot_assignment_api_support, coding_agent_model_selection`, with an `agentAssignment` input (`target_repo`, `base_branch`, `custom_instructions`, `custom_agent`, `model`). https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-via-the-api. [verified]
45. Runner: "By default, Copilot cloud agent runs on a standard GitHub-hosted GitHub Actions runner (`ubuntu-latest`)"; organizations may "Choose between a standard GitHub-hosted runner or a labeled runner from a specific runner group", including "self-hosted runners that have access to internal resources", and repositories override via `runs-on` in `.github/workflows/copilot-setup-steps.yml`. https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-for-organization/configure-runner-for-coding-agent. [verified]

## What others do

Descriptive patterns, each pointing to the findings that support it.

- **Polling a tracker into fixed concurrency slots is the dominant open-source shape.** Symphony's spec (poll every 30 s, `max_concurrent_agents`, `available_slots` formula), Baton (`polling.interval_ms`, `max_concurrent`), Multica's daemon (push with "polls periodically as a backstop", 20 runs per daemon / 6 per agent), and kari-website's 15-minute tick plus `MAX_IN_FLIGHT` all converge on "slots filled from a ranked queue"; none of the hosted products expose a slot scheduler. (Findings 1, 6, 65, 66, 67.)
- **Scheduling by wall clock, not completion, is what every hosted product offers.** Routines (minimum 1 hour), Desktop tasks, Codex automations, Copilot automations (hourly/daily/weekly), Jules scheduled tasks, Actions `schedule` (5-minute minimum, delays under load, 60-day auto-disable on public repos). Event triggers are PR/release (Routines), issue-opened/PR-opened (Copilot), label/assign/comment (claude-code-action, Copilot, OpenHands). Only openclaw's `workflow_run` gate and Multica's queue-on-offline behave like "start when the previous thing finished". (Findings 28-32, 38, 43, 49, 55, 62, 67.)
- **Agent definition as Markdown with frontmatter recurs independently.** kari-website `agents/*.md`, Baton `WORKFLOW.md`, gh-aw `.md` compiled to `.lock.yml`, Claude Desktop `SKILL.md` tasks, uv's `agents/prompts/*.md` with JSON schemas. (Findings 3, 32, 58, 63, 66.)
- **Deterministic shell around a probabilistic agent.** uv gates each stage on structured JSON output validated against a schema and persists context to a branch; toolhive-studio inserts a shell "Hard gate — Verify test fails" between agent phases and caps labels at 3 per run; gh-aw makes agents read-only and applies writes in separate validated jobs; Bernstein keeps "no model in the coordination loop"; kari-website's shortlist and liveness scripts play the same role. (Findings 16, 17, 58, 59, 63, 68.)
- **Write authority is scoped by identity and label, not trusted from the agent.** uv commits as a dedicated GitHub App bot and pushes context to a sibling repo; toolhive-studio and dyad mint GitHub App tokens per run; kari-website requires `agent/*` + `agent-pr`; gh-aw caps `create-pull-request` at 1 and `add-labels` at 5; Routines push to `claude/` branches under the user's own identity. No tool found implements "only work issues authored by the bot" as a gate; the closest is uv filtering issues to its own repository URL and toolhive-studio excluding issues with existing `fix/auto-*` branches. (Findings 18, 30, 58, 59, 63.)
- **Model tiering per stage is done by splitting stages across workflow steps or agents.** toolhive-studio uses Sonnet for triage and Opus for test-writing in separate steps; uv passes `effort: high` per step; Multica selects a model per agent; gh-aw selects an engine per workflow; kari-website states the split in one prompt section. Routines, Copilot and Jules select one model per routine/session. (Findings 9, 31, 44, 59, 58, 63, 67.)
- **Cost accounting is per run and client-side.** Claude Code's `total_cost_usd`/`modelUsage` (explicitly "client-side estimates"), Symphony's token totals from app-server events, Multica's "what each run cost, per agent and per issue", gh-aw's `max-ai-credits`, SWE-agent's cost limits, kari-website's usage JSON. Hosted products bill against a subscription pool with no per-run figure (Routines, Codex cloud, Copilot premium requests). (Findings 7, 30, 34, 35, 40, 46, 63, 65, 67, 71.)
- **Cost caps exist as per-run budgets, not fleet budgets.** `--max-budget-usd` (print mode), gh-aw `max-ai-credits` and `max-daily-ai-credits` per workflow, SWE-agent per-instance and total limits, Cursor's spend limit; kari-website's $2 retry ceiling is the only cross-run rule found. (Findings 8, 34, 50, 63, 71.)
- **Fallback is a harness feature for overload, and quota exhaustion is handled outside the harness or not at all.** `--fallback-model` is documented for "overloaded or not available"; kari-website had to add a 429 retry around it; Symphony uses exponential backoff on abnormal exit; no hosted product documents a fallback model. (Findings 8, 34, 65.)
- **The laptop as runner is viable and used, with the public-repo caveat.** dyad schedules Claude on a self-hosted macOS runner; Cursor and Copilot both offer "your machine executes, vendor hosts the loop"; Multica's daemon and OpenClaw's Gateway run on the laptop; GitHub warns self-hosted runners "should almost never be used for public repositories". (Findings 45, 52, 57, 60, 67, 83.)
- **Chat channels are either "open a cloud session" or "push into a running local session".** Slack→cloud session (Claude), Slack/Linear/GitHub→cloud VM (Cursor), Teams/Slack/Jira→Actions (Copilot) on one side; Claude Code Channels, OpenClaw and Multica daemons on the other. All laptop-side designs use outbound-only transports (Telegram long polling, Slack Socket Mode, Discord Gateway). Resuming a specific session from a message is supported by Claude Code (`--resume <id>`, same machine) and by the Channels design (one persistent session), but not by Routines or Slack, which create a new session per event. (Findings 29, 33, 36, 42, 50, 79-84.)
- **Hosted agents require the vendor's identity model.** Routines, Remote Control and `--cloud` need a claude.ai subscription login, not an API key; Copilot bills the automation's creator; Codex cloud shares the ChatGPT allowance; Jules uses Google One tiers. A model-agnostic fleet cannot be built on any of them. (Findings 30, 31, 40, 43, 48, 80.)
- **Security incidents cluster around write paths and runner persistence.** gh-aw's five advisories in seven weeks, GitHub's self-hosted runner warning, kari-website's own OOM/suspend/stale-clone incidents. (Findings 13, 14, 57, 64.)

## Open questions for the thinking run

1. **Build, adopt, or adopt-and-extend.** The evidence leaves three positions open:
   - *Build* (kari-website's path, finding 27). Supported by: no tool provides pull-on-completion into a slot *and* bot-authored authority in script *and* Telegram *and* model-agnostic (Tables 1-3); the predecessor's dispatcher is ~900 lines with a test harness and known incident fixes already encoded (findings 13-15); Symphony's own guidance is to "fork, study, or rebuild" (finding 65). Against: the predecessor accumulated prompt-only rules (findings 6, 9, 18-24) that the process spec forbids.
   - *Adopt a tracker-polling orchestrator* (Symphony-shaped: Baton, Multica, Bernstein; findings 65-68). Supported by: the slot/poll model matches spec 6.2 exactly; Multica adds cost per run, retries and a Telegram channel. Against: Baton is a 23-star project last pushed 2026-03-27; Multica replaces GitHub issues as the tracker, which conflicts with "issue as system of record" (design tree R6.Q4, R8.Q1); Bernstein is a run-graph executor, not a backlog puller; none enforce author-based authority.
   - *Adopt GitHub Actions on the self-hosted runner* (findings 53-62). Supported by: three-plus production pipelines (uv, toolhive-studio, dyad) demonstrate issue→triage→fix with schema-gated stages, label handoffs, App-bot identity and concurrency groups; model tiering per step is native; cost is the CLI's JSON. Against: `schedule` has a 5-minute floor, load delays and a 60-day auto-disable on public repos (finding 55); self-hosted runners on a public repo carry GitHub's explicit warning (finding 57); concurrency groups queue but do not rank a backlog (finding 56); claude-code-action has an open p1 cron-auth bug (finding 54).
   Which combination the thinking run picks bears on findings 1-27, 53-68.
2. **Can a hosted trigger be the watchdog while the laptop is the executor?** Routines' `/fire` API and GitHub-event triggers (findings 29-31), Copilot's assign-by-API (44), and Actions `repository_dispatch` (55) can all *start* something; only Actions can start something on the laptop. Options: Actions `schedule`/`issues` as the wake-up with the laptop runner doing the work; a laptop systemd service as the sole scheduler (predecessor); a hybrid where Telegram and GitHub webhooks both wake a local scheduler. Bears on findings 1, 28-31, 55-57, 62.
3. **Is the self-hosted runner acceptable on a public repository?** GitHub says "almost never" (finding 57); the existing deploy job already runs there (CLAUDE.md of char-matrix-dashboard). Options: restrict agent workflows to non-fork events and bot-authored issues (uv-style identity checks, finding 58), JIT ephemeral runners, or keep agents off Actions entirely and use Actions only as a trigger. Bears on 57, 58, 62.
4. **How is bot-authored authority enforced when no tool provides it?** The closest instances are uv's "issue must belong to repository" check, toolhive-studio's label/branch filters, and gh-aw's actor filtering (findings 58, 59, 63). Options: extend kari-website's `backlog-shortlist.sh` with an author filter; a gh-aw-style separate "writer" job; a Symphony `dispatchable` adapter flag. Bears on 16, 58, 59, 63, 65.
5. **Where does quota-exhaustion fallback live?** No harness or product handles 429-quota fallback (finding 8 vs 34); only the predecessor's retry does. Options: keep the dispatcher retry; use `--fallback-model` chains and accept quota gaps; alternate providers per stage (model-agnostic harness). Bears on 8, 34, 65.
6. **Telegram: build on the Bot API or adopt Claude Code Channels or OpenClaw?** Channels is a research preview, Claude-only, cannot start a session and needs a persistent `claude` process (finding 79); OpenClaw is harness-agnostic but a large dependency (83); the Bot API is simple, free and long-poll friendly (77, 78) and the predecessor's bash is a worked reference (10). Also open: whether grilling sessions should be resumed by id (`--resume`, same machine, finding 36) or re-created from the issue (the "Don't rely on session resume" option in the same doc). Bears on 10, 36, 77-83.
7. **Should per-run cost caps be the fleet's budget mechanism?** Only per-run caps exist (`--max-budget-usd`, gh-aw credits, SWE-agent limits; findings 34, 63, 71); the predecessor's $2 ceiling is a per-retry rule. Options: per-stage budgets passed to the harness; a scheduler-level daily cap computed from usage records; gh-aw-style `max-daily-ai-credits`. Bears on 7, 8, 34, 35, 63.
8. **Which tools' security posture to borrow.** gh-aw's read-only agent + validated writer jobs and its five advisories (63, 64), uv's sibling-repo context branch with short-lived tokens (58), the predecessor's `--dangerously-skip-permissions` accepted risk (27) vs Claude Code's `--permission-prompts none`/`dontAsk`/`--bare` (34). Bears on 27, 34, 58, 63, 64.
9. **Is Multica's "queue while runtime offline" the right answer to laptop sleep?** Multica queues runs for an offline daemon and re-claims on restart (67); Desktop tasks run one catch-up (32); the predecessor inhibits sleep and accepts missed slots (14). Bears on 14, 32, 67.

## Confidence

Strong: the kari-website checklist (read directly from the scripts and prompts with line numbers), the Claude Code surface (routines, desktop tasks, headless CLI, channels, remote control, sessions, cost tracking were all fetched from current official pages that cite CLI versions up to v2.1.286), the GitHub Actions platform facts (schedule limits, concurrency semantics, self-hosted runner warnings), the seven public workflow files (fetched verbatim from each repository's default branch), the Symphony spec, and the Telegram Bot API limits. Moderate: Copilot billing, where two official pages use different vocabularies (premium requests vs. AI credits) and the request-based page is labelled legacy; Codex cloud, where the docs describe UI and CLI triggers but no API, and the issue-mention behaviour came from a search summary rather than the fetched page; Multica, Bernstein and Agent Orchestrator, whose capabilities are recorded from READMEs and two doc pages, not from running them. Thin: Temporal, Dagger, Prefect and n8n as coding-agent orchestrators (no primary production instance found; the only artefacts are small community repos), the OpenHands self-hosted resolver (not found in the current tree; its archived predecessor dates from 2024), and gh-aw's cost reporting (budget keys exist, per-run records were not documented on the pages read). With more time I would read Symphony's Elixir implementation for its tracker adapter interface (to see what a GitHub adapter would need), Multica's `SELF_HOSTING.md` and security-model pages, gh-aw's threat-detection and concurrency reference pages, the Codex app-server protocol that Symphony drives, and the Claude Code `self-hosted-environments` pages to confirm they are Team/Enterprise-only; and I would run `claude-code-action` on the existing ThinkPad runner once to measure cron-trigger auth (issue #814) and minutes-to-start against a systemd tick.
