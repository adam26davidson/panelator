# Token and cost efficiency

Status: complete, with three explicit gaps: kari-website's records attribute
cost by model, not by pipeline stage (finding 7); the superpowers plugin's
claimed quality effect was never measured (finding 15); RouteLLM was read at

Date: 2026-10-02

## Question

How do agent-driven projects keep token cost per merged change down without
losing quality, and what did kari-website actually measure? Specifically: the
predecessor's own cost record and its sequence of cadence decisions; current
vendor documentation on prompt caching (behaviour, TTLs, pricing, what breaks
a cache) and how the candidate harnesses exploit it; context management levers
(compaction, trimming, subagent isolation) and any published measurement of
their effect; results of routing a stronger model to judgment and a cheaper one
to implementation, including failures; the per-turn cost of always-loaded
guidance material (`AGENTS.md`, skill descriptions, MCP schemas); and batching
small issues plus what CI minutes cost on hosted versus self-hosted runners.

## Findings

### A. kari-website's own record

1. **Dataset and totals.** [verified] The dispatcher kept 203 per-run result objects over 40 days (2026-08-23 to 2026-10-02). Summing `total_cost_usd`: **$1,766.90** total; `issue-pipeline` 176 records (161 primary + 15 `-retry`) **$1,704.09**, mean $9.68 per tick; `backlog-grooming` 27 records **$62.81**, mean $2.33. Source: `~/.local/state/kari-website-automation/usage/`, written by `dispatch.sh` lines 377–416; retention 180 days (`KARI_AUTOMATION_USAGE_RETENTION_DAYS`, dispatch.sh line 100). These are client-side estimates (finding 20), and the README's own caveat says to compare with the subscription usage page before trusting them as absolute (README "State" section).

3. **Per-tick cost distribution.** [verified] Over the 141 successful, non-retry pipeline ticks: p25 $6.59, median $7.45, p75 $12.64, p90 $17.05, mean $11.35. The most expensive tick spawned 9 subagents and cost $45.20. Grouped by `subagent_stats.spawned` (all non-error pipeline ticks): 0 subagents → mean **$0.63** (n=12); 1 → $5.45 (n=24); 2 → $9.14 (n=65); 3 → $17.76 (n=31); 4 → $16.22 (n=11); 5 → $14.80 (n=8). So the orchestration floor of a tick that finds nothing to do is about $0.63, and spend is driven by how many workers/reviewers a tick dispatches, which is what the README predicted: "Steady-state usage tracks the cap more than the cadence" (README lines 515–520).

5. **The README's throughput model.** [verified] "The ceiling on worker starts per hour is `ticks/hour × MAX_IN_FLIGHT`"; "Steady-state usage tracks the cap more than the cadence. A PR normally needs several ticks to go green, get reviewed, and merge ... what it actually spends is roughly proportional to how many PRs are open at once. Cadence mostly sets the orchestration floor and how promptly a finished PR gets noticed." "So: cut the cap to spend less, cut the cadence to spend less *often*." (README lines 489–523.) Finding 3 is consistent with this; finding 2 shows ticks/PR between 1.8 and 3.8.

6. **Cache behaviour in the fleet.** [verified] Summing `modelUsage` across all 203 records (whole tree, subagents included, see finding 20): cache reads **1,283M tokens**, cache writes **46.8M**, uncached input ~1.90M (of which 1.83M is Haiku, finding 7), output **11.9M**. Excluding Haiku, **96.5% of input-side tokens were cache reads**. Read:write ratios per model: `claude-fable-5` 294.7M:19.0M (15.5:1), `claude-opus-5[1m]` 827.4M:17.3M (48:1). Every top-level cache write recorded was 1-hour TTL (`usage.cache_creation.ephemeral_1h_input_tokens` equals `cache_creation_input_tokens` in every record), matching Claude Code's subscription default (finding 22). Approximate decomposition for `claude-fable-5` at list price: reads 294.7M × $1.00 = $295; writes 19.0M × $12.50–$20 = $238–$380; output 4.52M × $50 = $226; uncached input negligible. Output and cache *writes* dominate, not raw input. (The recorded fable-5 total of $821 sits inside that range; the exact split is unverifiable from the records.)

7. **Spend by model, as a proxy for stage.** [verified data; stage attribution is inference] `modelUsage.costUSD` summed across records: `claude-fable-5` $821.00 (111 sessions), `claude-opus-5[1m]` $645.08 (124), `claude-fable-5-1` $205.20 (27), `claude-opus-5` $87.19 (36), `claude-opus-5-5` $6.01 (4), `claude-opus-5-5[1m]` $0.57, `claude-haiku-4-5-20251001` $1.85 (160 sessions, 1.83M uncached input tokens, 4.4k output: Claude Code's background model, finding 25). Under the stated policy "judgment gets fable, implementation gets opus. Validation, plan, and review agents run on fable ... Worker and fix agents always run on opus" (issue-pipeline.md lines 792–799), the **judgment tier cost $1,026 (58%) and the implementation tier $739 (42%)**. The orchestrator itself runs on fable (frontmatter line 5), so the fable share includes orchestration. **Not found:** no per-stage attribution exists; the result object has no per-subagent breakdown, only `subagent_stats.by_type` counts (all `general-purpose`). Reconstructing plan vs review vs validation cost would need `--output-format stream-json` with `parent_tool_use_id` (finding 27).

8. **Spend lost to usage limits.** [verified] 25 records carry `api_error_status: 429` and one `529`; the 429 ticks cost **$79.95 (4.5% of all spend)** before dying. Fifteen `-retry` records cost $25.21. Issue #515 records the incident that motivated the retry: "the Fable quota went at 00:12 and was still exhausted 14h later, so the pipeline is down for the rest of the quota period even though its configured fallback is healthy", because `--fallback-model` "only covers capacity/overload errors" (README "Fallback model"; #515 verified it on the host with two `claude -p` calls).

9. **Cost-capped fallback retry.** [verified] `dispatch.sh` lines 561–590: retry at most once, only when the result object has `api_error_status == 429`, and only if `total_cost_usd <= KARI_AUTOMATION_RETRY_COST_LIMIT` (default $2), because "failing at session start costs ~2s and $0 ... a limit hit deep into a tick has already paid for that work, and re-running bills it twice". The playbook separately forbids downgrading judgment work: "if spawning a fable-tier subagent ... fails with a usage-limit error, POSTPONE that item ... never downgrade planning or the review gate or issue validation to a smaller model" (issue-pipeline.md lines 807–811). Process-spec section 6.5 already carries this forward.

10. **Batching rule as deployed.** [verified] Phase B: "clustered small issues should SHARE a worker rather than trickle through one per tick (each PR costs a full CI run) ... Combine only when ALL hold: each is small and mechanical ... never combine issues that change app behavior; they share a file or a tight area; at most three issues share one combined branch; none carries `has-dependencies`, `needs-clarification`, or `blocked`" (issue-pipeline.md lines 596–609). "Combining couples their fates — a review finding on one holds the whole PR" (lines 613–615). Grooming adds consolidation upstream: "≥3 small open issues that are really one piece of work get folded into the most fully specified member as an umbrella ... one family per tick, ≤6 members" (#548, commit 12a7b79). Examples of batch PRs: #130, #169, #526. **Not found:** no measurement of tokens or CI minutes saved by batching.

11. **CI cost in the predecessor.** [verified] The repository is public (`gh repo view`: `visibility=PUBLIC`), so hosted standard runners cost nothing (finding 35). Last 200 runs: `CI` 75 runs, mean wall-clock 210 s; `Visual review` 48 runs, 147 s; `Deploy` 23 runs (includes environment-approval wait). `ci.yml` and `visual-review.yml` use `concurrency` with `cancel-in-progress: true`; only `visual-review.yml` has a `paths:` filter; every job sets `timeout-minutes` ("Without one a hung step ... runs toward GitHub's 6-hour default, burning runner minutes", ci.yml comment). Had the repo been private, 75 × 3.5 min at the Linux 2-core rate ($0.006/min) is ≈ $1.60, two orders of magnitude below model spend.

12. **Machinery share, as the predecessor measured it.** [verified] "Two thirds of the agent PRs merged 2026-08-19..21 were tooling for the pipeline's own environment; eight touched the website" (commit 75580b8, #405); by 2026-08-28 "68 of 114 open issues (60%) are `tooling`" and "a merged PR spawns 2–3 while closing 1. Since 08-21: 104 opened vs 49 closed" (#548). Cost per *product* PR is therefore well above the $24.30 blended figure in finding 2; the merged-PR dataset carries no `automation` label (it is applied to issues), so the split is Agent 7's to reproduce from titles.

### B. Guidance-file cost in the predecessor

13. **What is always loaded, and what it weighs.** [verified sizes; token counts are a 4-chars/token estimate per Anthropic's pricing FAQ "1 token is approximately 4 characters"] Claude Code loads CLAUDE.md (or AGENTS.md), auto memory, MCP tool names and skill descriptions into every session, including every `-p` tick and every subagent ("The subagent loads CLAUDE.md too ... it counts against the subagent's context", context-window page). The docs' worked example weighs the fixed startup content at: system prompt ≈ 4,200 tokens, project CLAUDE.md 1,800, auto memory 680, skill descriptions 450, environment 280, deferred MCP tool names 120 (context-window page, event table).

14. **The #659 trim.** [verified] `git show 5370ac4^:CLAUDE.md | wc` = 458 lines, 29,120 bytes; after: 276 lines, 15,134 bytes (≈ 7.3k → 3.8k tokens). The PR states the rationale: "`CLAUDE.md` is loaded into context at the start of every session, so its length is a fixed per-session cost paid whether or not the work touches those subjects", and the method: "the rule stays inline, the reference detail moves to `docs/`, and a **trigger line** — 'if you are about to do X, read Y FIRST' — routes to it"; six new `docs/*.md` files (568 insertions). Two items were deliberately kept inline because they "have silent, expensive failure modes that a pointer would not convey in time". Today CLAUDE.md is 9 lines containing `@AGENTS.md`, and AGENTS.md is 293 lines / 16,298 bytes, so the file has grown back past its post-trim size. **Rough magnitude:** ~3.5k tokens × (176 ticks + 354 subagents spawned) ≈ 1.9M fewer cache-write tokens over 40 days, ≈ $25–40 at Fable/Opus write rates, i.e. about 2% of spend. **Not found:** no before/after measurement of adherence or spend was recorded for #659; the measurable benefit is the write-token arithmetic above.

15. **The superpowers plugin.** [verified sizes; effect unverified] `hooks/hooks.json` registers a `SessionStart` hook on `startup|clear|compact`; `hooks/session-start` injects the entire `skills/using-superpowers/SKILL.md` wrapped in `<EXTREMELY_IMPORTANT>` as `additionalContext`. That file is 3,108 bytes in 6.3.0 (≈ 780 tokens) and 3,192 bytes in 6.4.1; the 14–15 skill descriptions total ≈ 3.4 KB (≈ 850 tokens) in the skill index. So the plugin added roughly **1.6k tokens per session and again after every compaction**, on top of pressure to route work through skills. Issue #540's stated reasons: "every session in this repo — including **every automation fleet tick and worker** — pays the SessionStart injection ... ticks run ~$1–7 each on Fable/Opus" and "Skills written as enforcement scaffolding for older models measurably degrade Claude 5 output". **Not found:** no measurement of that degradation exists in the repository or the issue; the commit (73b85a2) attributes the view to "ecosystem guidance (including from the plugin's own author)" without a citation.

16. **Vendor guidance on size.** [verified] Claude Code: "Aim to keep CLAUDE.md under 200 lines by including only essentials" (costs page); "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence ... [Imports] help you organize a long file but don't reduce its context cost, because imported files also load at launch" (memory page); auto memory loads "the first 200 lines or 25KB"; block-level HTML comments are stripped before injection; `/doctor prompt-audit` audits these files. Codex: `project_doc_max_bytes` defaults to **32768** bytes, "Maximum total bytes of project instruction content across all selected environments" (`codex-rs/config/defaults.toml`, `config.schema.json`; `DEFAULT_PROJECT_DOC_MAX_BYTES: usize = 32 * 1024` in `config_toml.rs`), and `skills.max_context_tokens` "Defaults to 2% of the model's context window". OpenCode: `instructions` takes an array of paths/globs; no size cap documented.

17. **MCP schema cost.** [verified] Claude Code defers MCP tool definitions by default: "only tool names and server instructions enter context until Claude uses a specific tool"; "Set `ENABLE_TOOL_SEARCH=auto` to load schemas upfront when they fit within 10% of the context window, or `ENABLE_TOOL_SEARCH=false` to load everything" (costs and context-window pages). Output is capped: warning above 10,000 tokens, limit 25,000 (`MAX_MCP_OUTPUT_TOKENS`). The docs explicitly prefer CLI tools: "Tools like `gh`, `aws`, `gcloud` ... are still more context-efficient than MCP servers because they don't add any per-tool listing". `/usage` attributes plan usage to "skills, subagents, plugins, and individual MCP servers". The design rationale: tools are kept as "lightweight stubs (just the tool name, with `defer_loading: true`) ... always present in the same order" so the cached prefix never changes (claude.dev lessons post, 2026-04-30).

### C. Prompt caching

18. **Anthropic cache mechanics.** [verified] Pricing multipliers on base input: 5-minute write 1.25x, 1-hour write 2x, read 0.1x (0.025x on Fable 5.1 and Mythos 5.1, 0.05x on Opus 5.5). "The cache is refreshed for no additional cost each time the cached content is used"; lifetime "is measured from the start of the request that writes or reads the cache entry, not from the end of its response". Minimum cacheable prefix: 512 tokens (Fable 5/5.1, Opus 5/5.5, Sonnet 5.5), 1,024 (Sonnet 5/4.6/4.5, Opus 4.8), 4,096 (Haiku 4.5, Opus 4.5/4.6); shorter prompts "will be processed without caching, and no error is returned". Hierarchy `tools → system → messages`: a change at one level invalidates it and everything after. Invalidators: any tool-definition change, adding/removing images, thinking parameters, `effort`, `tool_choice` (messages level only), web-search/citations toggles. Two modes: automatic (one top-level `cache_control`, breakpoint placed on the last cacheable block) or explicit, max 4 breakpoints, 20-block lookback. Break-even stated by the pricing page: "caching pays off after one cache read for the 5-minute duration (1.25x write), or after two cache reads for the 1-hour duration (2x write)".

19. **Anthropic prices (per MTok, 2026-10-02).** [verified] Fable 5.1: $10 in / $12.50 5m-write / $20 1h-write / **$0.25 read** / $50 out. Fable 5: same except **$1.00 read**. Opus 5.5: $4 / $5 / $8 / $0.20 / $20. Opus 5: $5 / $6.25 / $10 / $0.50 / $25. Sonnet 5.5: $2 / $2.50 / $4 / $0.20 / $10. Haiku 4.5: $1 / $1.25 / $2 / $0.10 / $5. Batch API 50% off input and output, stackable with caching. 1M context at standard price for 4.6+ models. "Claude 4.7 and later models ... use a newer tokenizer ... approximately 30% more tokens for the same text." Tool-use system prompt adds 286 tokens on Opus 5/5.5 and Sonnet 5.5. Implication for finding 6: had kari-website's fable-5 cache reads been billed at Fable 5.1's read rate, $295 of reads would have been $74.

20. **What the harness's cost figures mean.** [verified] "The `total_cost_usd` and `costUSD` fields are client-side estimates, not authoritative billing data. The SDK computes them locally from a price table bundled at build time". On subagents: "`usage`: Excluded. Counts only the top-level agent loop"; "`total_cost_usd`: Included. Counts subagent requests alongside the top-level loop"; "`modelUsage` / `model_usage`: Included ... broken down by model" (agent-sdk/cost-tracking). This resolves the README's open caveat: kari-website's `total_cost_usd` totals *do* include worker, fix, plan and review subagents, and its `usage.*` token lines do not. For resumed sessions "Each result already includes the session's earlier spend" (v2.1.277+).

21. **OpenAI cache mechanics and prices.** [verified] "Prompt caching is enabled by default for supported OpenAI models"; minimum "1,024 visible input tokens" (GPT-5.6+); longest-prefix matching across "the first 2 and latest 50 explicit breakpoints" plus implicit boundaries; cached input at "0.1× uncached input rate" (0.05x on GPT-6.1 Sol); retention "30 minutes after its most recent write or reuse" on GPT-5.6+ via `prompt_cache_options.ttl`, earlier models "around 5 to 10 minutes of inactivity, up to one hour", with a `24h` option; any change to the "entire rendered prefix" breaks reuse, "including changes to model, tools, tool definitions, schemas (`text.format`), reasoning effort, verbosity, or context management". Prices per MTok (input / cached / output): gpt-5 $1.25 / $0.125 / $10; gpt-5-mini $0.25 / $0.025 / $2; gpt-5-nano $0.05 / $0.005 / $0.40; gpt-5.2 $1.75 / $0.175 / $14; gpt-5.3-codex $1.75 / $0.175 / $14; GPT-5.6-sol $4 / $0.40 / $20 (promotional through 2026-11-21). Batch 50% off; Flex matches batch; Fast 2x.

22. **How Claude Code exploits the cache.** [verified] Requests are ordered system prompt (tools) → project context (CLAUDE.md, memory, rules) → conversation, so turn-to-turn changes land at the end. Invalidators (each a one-time full re-read): switching models ("each model has its own cache"), changing effort on most models, turning on fast mode, connecting/removing an MCP server when tools are loaded upfront, plugin MCP changes, denying an entire tool without tool search, compaction, image eviction, upgrading Claude Code. Cache-safe: editing repo files, editing CLAUDE.md mid-session (does not apply until `/clear`/`/compact`/restart), permission-mode changes, skills and commands ("inject their instructions as user messages"), `/rewind`, spawning subagents. TTL buckets: main conversation (interactive, `-p`, SDK turns) gets **1 hour on a Claude subscription within plan usage, otherwise 5 minutes**; "Everything else", including subagents, compaction and session titles, gets 5 minutes unless `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL`/`subagentPromptCacheTtl` (v2.1.242+) or `ENABLE_PROMPT_CACHING_1H` says otherwise. Cache scope is "effectively scoped to one machine and directory"; for fleets, `--exclude-dynamic-system-prompt-sections` moves per-user context into the first user message to share the system-prompt cache across machines. `/usage` shows a `Prompt cache (main)` line with hit share, misses and likely cause (v2.1.251+/v2.1.260+). The documented consequence for 6-hourly ticks: "your first message after a break longer than the cache lifetime misses the cache and reprocesses your full context" (costs page), so with a 6h cadence the orchestrator's prefix is cold at every tick regardless of TTL, and the 1h TTL only helps within a tick.

23. **Codex, pi, OpenCode caching.** [verified] Codex's config reference has no caching keys; caching is the server-side automatic behaviour of finding 21. pi declares cache lifetimes per model in `models.json` (`"promptCache": { "short": 300, "long": 3600 }`, seconds) and its summarisation requests "explicitly disable prompt-cache writes because these one-off prompts are unlikely to be reused" (`compaction.md`); pi "supports both provider-specific implementations (Anthropic's cache_control and OpenAI's automatic caching)" (`models.md`). OpenCode's config page documents no cache controls. **Not found:** pi per-subagent model assignment in `models.md`.

### D. Context management

24. **Server-side context editing (Anthropic API).** [verified] `clear_tool_uses_20250919`: default trigger 100,000 input tokens, keep 3 tool uses, optional `clear_at_least`, `exclude_tools`, `clear_tool_inputs`; `clear_thinking_20251015`: keep last N turns or `all`; beta header `context-management-2025-06-27`; all active Claude models. Cache interaction: tool-result clearing "invalidates cached prompt prefixes when content is cleared", so "Use `clear_at_least` ... making cache invalidation worthwhile"; on Fable 5.1/Opus 5.5/Sonnet 5.5 "server-side context management never invalidates thinking blocks". Cleared tokens are reported in `context_management.applied_edits[].cleared_input_tokens`. Client-side SDK compaction is deprecated in favour of server-side. Claimed effect (claude.com/blog/context-management, 2025-09-29, internal evals): memory + context editing "+39% over baseline", editing alone "+29%", and "in a 100-turn web search evaluation ... reducing token consumption by 84%".

25. **Harness compaction and background spend.** [verified] Claude Code auto-compacts at a window of "about 967K tokens by default" on 1M-context models; `CLAUDE_CODE_AUTO_COMPACT_WINDOW` accepts 100,000–1,000,000, `--autocompact <auto|tokens>` per session (v2.1.221+). The compaction request "reads your prefix from the cache, so a mid-session `/compact` costs a fraction of what the context size suggests", but after the cache has expired it "reprocesses the full history as uncached input". Survives compaction: startup content, a structured summary, recently modified files, invoked skill bodies "capped at 5,000 tokens per skill and 25,000 tokens total"; skill descriptions do not reload. Background usage: "typically under $0.04 per session" for summarisation and status calls; the Haiku line in finding 7 ($1.85 over 160 sessions) matches. Codex: `model_auto_compact_token_limit` (unset = model default), `model_auto_compact_token_limit_scope` (`total | body_after_prefix`), `tool_output_token_limit`. pi: compaction when `contextTokens > contextWindow - reserveTokens` (reserve 16,384), keeping the most recent 20,000 tokens verbatim, never cutting between a tool call and its result. OpenCode: `compaction.auto` true, `prune` false, `reserved` buffer. **Not found:** Codex's default compaction threshold value.

26. **Subagent isolation: context yes, tokens no.** [verified] "Each subagent runs in its own context window ... returns only the summary"; "It also sends its own requests, which count toward the same usage limits as your main conversation" (sub-agents page). Costs page: "Delegate these to subagents so the verbose output stays in the subagent's context while only a summary returns"; "Agent teams use approximately 7x more tokens than standard sessions when teammates run in plan mode". Anthropic's research system (2025-06-13): "agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats"; on BrowseComp "token usage by itself explains 80% of the variance" in performance; Opus 4 lead with Sonnet 4 subagents "outperformed single-agent Claude Opus 4 by 90.2%". Context-engineering post (2025-09-29): subagents "return condensed summaries (typically 1,000-2,000 tokens)"; "just in time" retrieval of lightweight identifiers over pre-loading; tool-result clearing is "one of the safest lightest touch forms of compaction"; "the smallest possible set of high-signal tokens". Hooks as a lever: a `PreToolUse` hook can filter test output "reducing context from tens of thousands of tokens to hundreds" (costs page).

27. **Bounding a headless run.** [verified] `--max-turns` (exits with an error when reached; no default); `--max-budget-usd` ("Spend from subagents counts toward the cap ... spawning another subagent fails with `Budget limit reached`", v2.1.217+); `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` default 600,000 ms for background subagents after the final turn; `--bare` skips CLAUDE.md, hooks, skills, plugins, MCP and auto memory ("the recommended mode for scripted and SDK calls, and will become the default for `-p`"); `BASH_MAX_OUTPUT_LENGTH` default 30,000 chars; `--output-format stream-json` carries `parent_tool_use_id` on subagent messages, which is the only route to per-stage cost attribution (finding 7). kari-website used none of the budget flags; its only cost bound was the $2 retry threshold (finding 9) and the Claude Code default 10-minute background wait, which `KARI_AUTOMATION_BG_WAIT_CEILING_MS` mirrors (README "Telegram transport" alert list).

### E. Model routing by stage

28. **The predecessor's policy and its guards.** [verified] Commit d9f94e4 (2026-08-20): "Complex issues used to get a fable worker end-to-end, spending stronger-tier tokens on the typing as well as the thinking. Split those: a new read-only plan agent (fable) decides the approach, files, tests, and risks ... and an opus worker implements it ... Fix agents are now always opus too. Two guards keep quality where it was: the review gate stays fable, and an escalation valve stops the bare fix loop when the same findings survive two cycles — a fable planning pass on the diff plus findings feeds the next fix, and a third failure hands the PR to a human." Model names live in exactly one place (issue-pipeline.md lines 792–799; README lines 503–509 describe the split generically). Outcome data: finding 7's 58/42 split. **Not found:** no recorded incident attributing a defect or rework loop to the cheaper tier; `gh issue list --search "opus worker"` and `--search "escalation"` return no such report. The escalation valve's firing count is not recorded anywhere I could find; Agent 7's fix-cycle derivation is the place to look.

29. **Vendor-native stage routing.** [verified] Claude Code `opusplan`: "In plan mode: uses `opus` ... In execution mode: automatically switches to `sonnet`"; but "each plan-mode toggle is a model switch and starts a fresh cache" (prompt-caching page), a documented cost of routing by stage inside one session. `CLAUDE_CODE_SUBAGENT_MODEL` sets a default for all subagents; per-subagent `model:` frontmatter accepts `sonnet|opus|haiku|fable|inherit`. Costs page: "Use Sonnet for teammates"; "For simple subagent tasks, specify `model: haiku`". Codex offers per-stage *effort* rather than model: `plan_mode_reasoning_effort` and `agents.default_subagent_reasoning_effort` alongside `model_reasoning_effort` (`low` … `ultra`), and profiles select a model per invocation. OpenCode: per-agent `model`, plus `small_model` "for lightweight tasks like title generation".

30. **Aider's architect/editor split (2024-09-26, Aider's own benchmark).** [verified] Separating "describe the solution" from "conform to the edit format": o1-preview architect + DeepSeek editor 85.0%, o1-preview + o1-mini 85.0%, o1-preview + Claude 3.5 Sonnet 82.7%; Sonnet + Sonnet 80.5% vs 77.4% solo; GPT-4o + GPT-4o 75.2% vs 71.4%; o1-mini 61.1% → 70.7% with a GPT-4o editor. Failure/caveat: the top pairs used whole-file editing and are "probably not practical for interactive use with aider" because of slowness. This is a quality result, not a cost result; cost is not tabulated.

31. **Anthropic's lead/subagent routing.** [verified] See finding 26: Opus lead + Sonnet subagents outperformed single Opus by 90.2% on an internal research eval, with the explicit economic condition "tasks where the value of the task is high enough to pay for the increased performance". The context-engineering post adds that multi-agent architectures suit "complex research with parallel exploration", compaction suits "extensive back-and-forth", and note-taking suits "iterative development".

32. **Routing failure modes documented by vendors.** [verified] Switching models or effort mid-session discards the cache (finding 22); `opusplan` toggles are model switches (finding 29); OpenAI likewise lists "model ... reasoning effort, verbosity" among cache-breaking changes (finding 21). kari-website's own routing failure was operational, not quality: `fallback: opus` "sat in `issue-pipeline.md` for weeks ... without once doing so" because the flag covered capacity errors only (finding 8).

33. **RouteLLM (academic).** [verified abstract; details unverified] "RouteLLM: Learning to Route LLMs with Preference Data" (Ong et al., arXiv 2406.18665, v4 2025-02-23) trains routers on human preference data to "dynamically select between a stronger and a weaker LLM during inference", claiming to reduce costs "by over 2 times in certain cases—without compromising the quality of responses", with routers that transfer when the model pair changes. The per-benchmark numbers were not read; this is a lead for query-level routing, which no candidate harness implements natively.

### F. Batching and CI cost

34. **Batching evidence.** [verified] Finding 10 (predecessor rule, ≤3 mechanical issues per branch at dispatch; ≤6 per umbrella at grooming) and finding 12 (filing outpaced fixing 104:49). 35. **GitHub Actions pricing (2026-10-02).** [verified] "GitHub Actions usage is **free** for **self-hosted runners** and for **public repositories** that use standard GitHub-hosted runners." Included minutes for private repos: Free 2,000, Pro 3,000, Team 3,000, Enterprise Cloud 50,000 per month. Per-minute: Linux 1-core $0.002, Linux 2-core x64 $0.006, Linux 2-core arm64 $0.005, Windows 2-core $0.010, macOS 3–4 core $0.062. Storage: $0.25/GB-month shared, $0.07/GB-month Actions cache. Concurrency: "only a single job or workflow using the same concurrency group will run at a time"; with `cancel-in-progress: true` "any currently running job or workflow in the same concurrency group" is cancelled; by default one pending job is kept, `queue: max` allows up to 100. No statement on billing of cancelled jobs was found. ## What others do

- **Treat the cache as the architecture, not an optimisation.** Claude Code orders every request so stable content precedes volatile content, keeps tool stubs present in fixed order, injects skills and plan-mode instructions as messages rather than system-prompt edits, and forks compaction off the cached prefix (findings 17, 22, 25). pi declares cache lifetimes per model and skips cache writes for one-off summaries (finding 23). OpenAI makes caching automatic and warns that any prefix change, including model or effort, breaks it (finding 21). kari-website achieved 96.5% cache reads without doing anything beyond running Claude Code (finding 6).
- **Spend goes to output and cache writes, not raw input.** The fable-5 decomposition (finding 6), the 2x 1-hour write multiplier (finding 18) and the vendor advice to pick model and effort "at the top of a session" (finding 22) all point the same way.
- **Context isolation via subagents, with the explicit caveat that it does not save tokens.** Anthropic's docs and posts (findings 26, 31), the 4x/15x figures, and kari-website's worker/review/fix subagents.
- **Mechanical trimming of always-loaded material**: a 200-line CLAUDE.md target with path-scoped rules and on-demand skills (finding 16), a 32 KiB AGENTS.md cap in Codex (finding 16), deferred MCP schemas (finding 17), CLI tools preferred over MCP (finding 17), and the predecessor's trigger-line split (finding 14) and plugin removal (finding 15).
- **Stage-based routing with a strong model on judgment**: kari-website (plan/review/validate on fable, implement/fix on opus), Claude Code `opusplan`, Anthropic's Opus-lead/Sonnet-subagent system, Aider's architect/editor (findings 28–31). Codex routes effort rather than model (finding 29).
- **Server-side context editing rather than client summarisation** is Anthropic's recommended direction, with cache-aware thresholds (finding 24).
- **Cadence as a spend throttle**, moved up only to consume expiring allowances (finding 4), and run-level budget bounds (`--max-budget-usd`, `--max-turns`) available but unused by the predecessor (finding 27).
- **Combine small mechanical changes into one PR** because "each PR costs a full CI run", bounded to keep review findings from coupling unrelated work (finding 10).

## Open questions for the thinking run

1. **Cadence vs pull-on-completion as a cost model** (findings 3, 4, 5, 22). The predecessor's orchestration floor was ≈ $0.63 per empty tick and its prefix was cold at every 6-hour tick. Under process-spec 6.2 (work starts on completion, watchdog only), the floor is replaced by per-worker session startup. Options: one long-lived orchestrator session kept warm within TTL; short-lived per-task sessions with `--bare` and a minimal prompt; a hybrid where the scheduler is a script (no tokens) and only workers are model sessions.
2. **Which TTL for which bucket** (findings 6, 18, 22). All predecessor writes were 1h at 2x. Options: 1h everywhere (`ENABLE_PROMPT_CACHING_1H`), 5m for subagents and 1h for the orchestrator (the Claude Code default on a subscription), or 5m everywhere if sessions are short. The break-even is two reads per write for 1h.
3. **Model tiering under current prices** (findings 7, 19, 28). Fable 5 reads cost $1/MTok; Fable 5.1 reads $0.25; Opus 5.5 is $4/$20 with $0.20 reads. The 58/42 judgment/implementation split was measured against Fable 5 and Opus 5 prices. Options: keep fable/opus; Opus 5.5 for implementation; Sonnet 5.5 for fix agents; a single model with per-stage *effort* (the Codex approach); query-level routing (RouteLLM, no harness support).
4. **Per-stage cost attribution** (findings 7, 20, 27). Model is only a proxy for stage. Options: `stream-json` with `parent_tool_use_id` parsed by a script into a per-stage ledger; one headless session per stage (orchestrator as a script, each stage its own `claude -p` with its own result object); accept the proxy. Process-spec section 7 wants "Cost per merged PR, by model and stage".
5. **Budget bounds per run** (findings 8, 9, 27). The predecessor lost 4.5% of spend to 429-killed ticks and bounded nothing except the $2 retry. Options: `--max-budget-usd` and `--max-turns` per stage with values derived from finding 3's distribution (e.g. p90 ≈ $17 per tick); subagent depth/concurrency/spend caps in the SDK; a fleet-level daily cap in the scheduler.
6. **Guidance-file shape** (findings 13–16). AGENTS.md is 293 lines again after a trim to 276. Options: enforce a line or byte cap in CI (Codex's 32 KiB is a precedent); split into a short always-loaded file plus path-scoped `.claude/rules/` and on-demand skills; measure adherence rather than size. This overlaps Agent 1's question 1.
7. **Plugins and skills as always-on overhead** (findings 15, 17). The predecessor removed a ~1.6k-token-per-session plugin on an unmeasured quality claim. Options: no plugins in headless runs (`--bare` plus explicit `--plugin-dir`), plugins only for interactive use, or measure first.
8. **Context editing vs compaction vs fresh sessions** (findings 24–26). Options: rely on harness auto-compaction (late, at ~967K on 1M models); set a lower `--autocompact`; use the API's `clear_tool_uses` with `clear_at_least` (needs SDK-level control, not available through `claude -p`); design stages short enough that no compaction happens. Only the API's server-side editing has a published measurement (−84% tokens, internal eval).
9. **Batching policy** (findings 10, 12, 34). Options: combine at dispatch (≤3), at grooming (≤6), or in the plan stage from the spec; what classes may be combined (predecessor: mechanical only); whether CI cost even matters for a public repo (finding 35 says hosted minutes are free, so the remaining batching benefit is fewer review and fix cycles, which is a token question).
10. **CI runner placement** (findings 11, 35). Hosted standard runners cost nothing for a public repo; self-hosted costs laptop availability and HIL is self-hosted by necessity. Options: hosted for everything except HIL; self-hosted for everything to keep one runner model; hosted with `cancel-in-progress` and path filters as the predecessor did.
11. **Fix-loop limit as a cost bound** (findings 2, 28). Each fix cycle costs a review (strong model) plus a fix (cheaper model) plus a CI run; the predecessor's valve re-planned after two surviving cycles and escalated after three, but how often it fired is unrecorded. The threshold values are open until Agent 7 reports fix cycles per PR.

## Confidence

Strong where the evidence is a dataset or a vendor page read today: the kari-website spend totals, per-tick distribution, cache ratios and cadence chronology come from 203 raw result objects and commit messages and can be re-derived with the `jq`/`awk` method described; the Anthropic, OpenAI, Claude Code, Codex (source), pi (pinned commit) and GitHub pricing facts are quoted from current primary pages. Moderate on the cost-per-PR figure, which depends on the `agent-pr` label as the ownership signal and mixes grooming and failed ticks into the numerator. Thin on effects: no source here measures what a guidance-file trim, a plugin removal, or PR batching saved; the only measured context-management effect is Anthropic's internal eval; routing evidence is quality-side (Aider, Anthropic) rather than cost-side, and RouteLLM was read at abstract level. With more time I would parse the predecessor's 139 tick logs for subagent dispatch lines to attribute spend per stage, read the RouteLLM paper body, fetch Codex's compaction defaults from `codex-rs` source, and read pi's `settings.md` and `sdk.md` for per-subagent model and cost reporting.
