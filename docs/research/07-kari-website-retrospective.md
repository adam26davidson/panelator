## Findings

### A. Timeline of structural changes

1. [verified] **Pre-fleet groundwork (2026-07-12 to 2026-08-18).** CI with lint/test/e2e plus Renovate auto-merge of non-major updates landed 2026-07-12 (`55a9c81`); deploys became gated on CI success 2026-08-01 (`e28ff85`); the `issue-lifecycle` workflow syncing the `in progress` label with linked PRs landed 2026-08-04 (`4b9cab2`, PR #30); the coverage ratchet 2026-08-04 (`d9be9f6`, #36); parallel-session and worktree conventions in CLAUDE.md 2026-08-07/09 (`891e3dd` #125, `8453d17` #166, stated reason: "Lessons from running many concurrent issue branches"); Claude visual review of UI PRs 2026-08-16 (`d29047a` #203, reason: "features have shipped green with obvious visual defects"); approval-gated test→prod deploy 2026-08-18 (`e8046d1` #230). ### C. The pagination and completeness bug

29. [verified] **Cause.** Phase B step 1 used `gh issue list --state open --json number,title,labels,body` with no `--limit` and no `createdAt`. "`gh issue list` defaults to 30, ordered newest-first. The repo currently has 88 open issues, so a literal run of that command shows the orchestrator only the 30 most recently created... The older backlog... is not evaluated and rejected on those ticks; it is never in the list at all" (#484, filed 2026-08-24 07:40). **Evidence the filer used:** "Every merged pipeline PR closed an issue at most 3.3 days old; the median is under a day and a half. Meanwhile #172 (Aug 9), #232 (Aug 17), #265 and #266 (Aug 19) have never been claimed." **Non-determinism:** the table in #484 shows picks of #272 and #273 that a newest-30 window could not have contained, so "the truncation is not happening on every tick. The orchestrator sometimes widens the query on its own initiative... the backlog's tail is visible on some ticks and invisible on others, and nothing in the run summary distinguishes the two." Fixed 4 minutes after filing: `1e980c7` #485 (`--limit 500`, `createdAt` as the ordering key, run summary names the oldest ready issue not picked).

30. [verified] **Second fix moved listing out of the prompt.** #590 (2026-08-30) introduced `backlog-shortlist.sh`, which "paginates the whole open backlog through the REST API (no `--limit` truncation, no lagging search index)" and prints `*_omitted` counts because "a slice that silently dropped its tail would read exactly like a complete one, which is how #484's truncated candidate list impersonated a working oldest-first rule for three days" (`backlog-shortlist.sh` header lines 52-56). The playbook now says "If the script fails, skip Phase B this tick... never fall back to a bare `gh issue list`, whose defaults (30 results, newest first) are exactly the silent truncation the script exists to prevent" (`issue-pipeline.md` lines 462-465). The shortlist does not assert its count against a server-reported total; it relies on `--paginate` being "complete by construction" (header line 68).

31. [verified] **Residual instances of the same class.** The groomer still lists with `gh issue list --state open --limit 500` and closed issues with `--limit 100` in its prompt (`backlog-grooming.md` lines 80-83); the open backlog is 250 today, so the cap holds, but nothing checks it. The playbook and `claim-liveness.sh` also document the GitHub search index as "a second, lagging source" that must never be the sole basis for a destructive decision (`claim-liveness.sh` header lines 20-26; `issue-pipeline.md` lines 740-747, 131-135).

34. [verified] **Product vs machinery classification, method.** For each merged PR the changed-file list was fetched (`pulls/<n>/files`, 355 PRs, none empty). A path is "machinery" if it matches `^(automation/|.github/|scripts/|docs/|AGENTS.md|CLAUDE.md|README.md|renovate.json|.claude/|.codex/|.vscode/|appspec|docker-compose|.gitignore|eslint/prettier/tsconfig/vitest/playwright config|package(-lock).json|Cargo.toml|Cargo.lock|test-data/)` or is a test/e2e/`__tests__`/`tests/` file. Two aggregation rules were computed: **any-product** (a PR is product if it touches at least one non-machinery file) and **majority** (product if non-machinery files ≥ machinery files). Over all 114 merged agent PRs: any-product gives 82 product / 32 machinery (28% machinery); majority gives 61 / 53 (46% machinery).

35. The "eight touched the website" count is reproduced exactly by the majority rule; "two thirds" by the any-product rule. The PR-level list is in the method output (e.g. #290, #294, #311, #324, #326, #336, #371, #389 machinery; #262, #328, #330, #418 product). After that window the machinery share of merged agent PRs fell to 1/10, 4/26, 0/16, 0/9, 1/9, 0/4 per week (any-product rule). Separately, #548 (2026-08-28) recorded the backlog-side ratio: "68 of 114 open issues (60%) are `tooling`"; today 134 of 250 open issues (54%) carry `tooling`.

## What others do

Patterns recurring within this one system's record; descriptive.

- **Incident → mechanical backstop, with the prose kept as explanation.** Every laptop-level failure (drift, suspend, stale clone, orphans, 600 s kill, OOM, watch mode, fallback) was answered by a change to `dispatch.sh` or a unit file, each commit quoting the incident (findings 8-17, 50). Prompt-level failures (stale claims, listing, ranking) were answered by moving the decision into a script whose output the prompt consumes (findings 10, 29-30, 27, 57).
- **State in GitHub; laptop holds only logs, locks and rescues.** Recovery, retry and hand-over all depend on it (findings 11, 52, 58); the one state the pipeline needs that GitHub does not hold (a "review postponed" marker) was identified and never built (finding 16).
- **Positive-evidence-only before any destructive action**, and "a failing probe counts as life" (findings 54, 10, 30-31).
- **Every cap made visible** (`*_omitted`, run-summary "oldest not picked", `tick exited` trailer) after a silent truncation went unnoticed for days (findings 29-30, 55).
- **Usage controlled by two named tunables edited in one place**, retuned eight times in three weeks, three of them deliberately upward to spend an expiring allowance (findings 3-4, 56).
- **Judgment tier never downgraded; the price is wedging** when that tier is limited and `MAX_IN_FLIGHT` is 1 (findings 16, 19).
- **Agent labels used as channels no agent may write** (`priority`, `user-feedback`) once agent-set priority was judged bad (findings 27, 49, 57).
- **Machinery grows fastest at the start and is pushed back by policy**: 66-77% of agent merges in the first three days, near zero by September; the open backlog is still 54% tooling (findings 35, 46).
- **The human is reached by label + chat, with GitHub first**; asks are mostly host/infrastructure work and product decisions, median 16 h to clear (findings 42-43, 58).
- **Guidance files grow with every incident until trimmed for cost** (finding 51).

## Open questions for the thinking run

1. **Which prompt rules become scripts or GitHub rules.** Branch protection requires 0 reviews, so the review gate, ownership signals, serial merge and one-merge-per-tick are unenforced (findings 48-49); the validation gate is explicitly "not a scripted gate" (finding 49). Options the evidence leaves open: a required status check that a bot posts after the review gate; a CODEOWNERS/required-review slot held by the bot account; keep prose and measure escapes. Bears on process-spec sections 4.3, 5, 6.4.
2. **Behaviour when the judgment tier is rate-limited.** Postpone (current, wedged the fleet for ~20 h, #826) vs downgrade (rejected in prompt as losing independence from the implementing model) vs a second provider for the gate vs `MAX_IN_FLIGHT` > 1. Findings 16, 17, 19, 5.
3. **Cadence vs pull-on-completion.** Agent PRs take median 5.4 h open→merge at a 6 h tick, 75% need a post-open push, and each tick costs "orchestration tokens even when it finds nothing to do"; three upward retunes were made just to spend allowance. Findings 3, 36, 38, 56.
4. **Provenance and issue authority.** All 627 issues are authored by one account; provenance is a label the fleet applies to itself and did not exist for the first 206 issues; fleet filings run ~93% of new issues and 2-3 per merged PR. Findings 45-47; process-spec 4.3 (bot-authored only) assumes a distinct bot identity the predecessor never had.
5. **How to measure the product/machinery ratio.** Any-product and majority rules give 28% vs 46% machinery overall and both bracket the pipeline's own claim; label-based (`tooling`) gives a backlog ratio, not a merge ratio. Findings 34-35, 46.
6. **Completeness assertion.** The shortlist paginates but does not compare against a reported total; the groomer still uses a literal `--limit 500`; search-index lag is a second class of incompleteness. Findings 29-31; process-spec 6.4.
7. **Human-ask latency and leftover labels.** Median 16 h, one 245 h; three closed issues still carry `needs-human` because only the bot path strips it; replies made directly on GitHub strip nothing. Findings 42-43; process-spec 6.3.
8. **Where "left for a human" is recorded.** The escalation valve's outcome exists only in laptop logs; the hand-over count is not derivable from GitHub. Finding 39.
9. **Validation gate effect.** 27 validation comments since 2026-09-08 against 140 closes; no measurement of what it rejected exists in the record. Findings 47, 49.
10. **Laptop failure modes still open.** #322 (limit-killed tick strands claims) and #398 (local/CI coverage drift) remain open; no suspend, OOM or orphan recurrence is recorded but neither is any monitoring beyond `--status`. Findings 10-11, 15, 24; process-spec 6.1.
11. **Interactive vs pipeline split.** 54 maintainer-session PRs vs 114 pipeline PRs in the fleet era, with the structural work in the former. Whether that is a goal state or a gap is not something the record says. Finding 33.

## Confidence

Strong where the claim rests on GitHub data or commit messages: PR, issue, label-event and comment totals were fetched with full pagination and cross-checked against the search API totals; file lists and commit counts were fetched per PR; every timeline entry cites a commit hash and most cite the issue that motivated it. The "two thirds" reproduction is strong because both aggregation rules bracket the original claim and one reproduces its "eight" exactly, but the classifier is a path regex of my own, not the pipeline's (the pipeline used its judgment of "tooling for the pipeline's own environment"). Thin: anything that lives only in laptop logs — tick counts, costs, run summaries, escalation outcomes, outbound Telegram sends, alert firings — I report as file counts only; Agent 5 should read the 203 usage records. Recurrence statements of the form "no later incident recorded" are absence-of-evidence in issues and commits, not evidence from logs. Pre-2026-08-21 provenance of issues is unrecoverable from labels. With more time I would read the 139 dispatcher logs for per-tick phase outcomes (merges, validations, "left for a human", shortlist omitted counts), diff `issue-pipeline.md` at each of its 20-odd revisions to date every prompt rule, and read the comment threads of the 11 multi-round PRs to see whether findings repeated across cycles (the escalation-valve condition), which comment counts alone cannot show.
