## Question

Which coding-agent harness fits panelator's criteria from process-spec section 6.6 (open source; headless on our own runner; model-agnostic with many pluggable models; skills or an equivalent extension mechanism; cost controls and usage reporting; coexists with interactive Claude Code use, with model-agnostic and headless as hard requirements), and what does each candidate actually support today? Candidates given: pi, Claude Code headless plus the Claude Agent SDK, OpenAI Codex CLI, OpenCode. For each, from official docs and source at the current version: licence and activity; headless invocation (command, output formats, exit codes, run bounds); model support (providers, per-run and per-stage configuration, local models); extension mechanism (skills, plugins, hooks, MCP, custom tools, what each can intercept); cost and usage reporting; session persistence and resume (which the Telegram grilling bot depends on); sandboxing and permissions when unattended; known gaps from the issue tracker. Then a cited comparison table, the list of survivors of the two hard requirements, and the recommended hands-on task with its measurements.

### 2. Headless invocation

7. **pi**: `pi --print "<prompt>"` runs once and writes the final assistant text to stdout; `pi --mode json "<prompt>"` writes JSONL events then exits; `pi --mode rpc` reads JSONL commands from stdin and stays alive; a non-TTY stdin or stdout selects print mode automatically. Piped stdin is prepended to the first prompt; `@path` attaches files. (`packages/coding-agent/docs/cli.md` "Invocation and output"; `cli-integration.md` lines 9-16.) [verified]
8. **pi exit codes**: in print mode "A final assistant response with an `error` or `aborted` stop reason produces a nonzero exit status"; in JSON mode "A failed or aborted assistant response appears in the event stream but does not by itself produce a nonzero exit status. Inspect the events when success or failure matters." (`cli-integration.md` lines 30, 46.) `pi auth check` exits 0/1/2 for ready/not_ready/invalid (`cli.md` "Credential commands"). [verified]
9. **pi JSON event schema**: a `session` header (`version: 3`, id, cwd) then `agent_start`, `turn_start`, `message_start`, `message_update` (delta-only, with cumulative `usage` including `cost{input,output,cacheRead,cacheWrite,total}`), `message_end`, `tool_execution_start|update|end`, `turn_end`, `agent_end` (`willRetry`), `agent_settled`, plus `auto_retry_start|end` (default `maxAttempts: 3`) and compaction events. Strict LF framing; stdout reserved for JSONL, diagnostics to stderr; "A reader that stops consuming records can stall Pi when the pipe buffer fills." (`json.md` lines 1-120.) [verified]
10. **pi run bounds**: I found no `--max-turns`, cost-budget or wall-clock flag in `cli.md`, `settings.md`, `sdk.md` or `rpc.md`; a grep of all downloaded docs for max-turns, budget, turn limit and time limit only hits `thinkingBudgets`, `codemode.inlineBudget` and compaction token budgets. Bounding a run is therefore the caller's job (process timeout, or `agent_before_settle`/`turn_end` extension handlers which the docs say "can loop" if unguarded, `extensions.md` "Events and concurrency"). [verified absence]
11. **Claude Code**: `claude -p "<prompt>"` with `--output-format text|json|stream-json`, `--json-schema` for validated structured output, `--input-format stream-json` for multi-turn stdin. Exit code 0 on success, non-zero on failure; invalid flags go to stderr before the run; a failure inside the run (for example missing auth) "prints the failure as the result on stdout". SIGTERM exits 143 and records no result. Piped stdin capped at 10 MB. (https://code.claude.com/docs/en/headless.) [verified]
12. **Claude Code run bounds**: `--max-turns N` (print only, "Exits with an error when the limit is reached. No limit by default"), `--max-budget-usd` (print only, subagent spend counts, enforcement from v2.1.217; restored totals from `--resume` do not count). No wall-clock flag; background subagents keep `-p` open until done, with a default 10-minute idle ceiling set by `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` (`0` waits forever). (cli-reference "CLI flags"; headless "Background tasks at exit".) [verified]
13. **Claude Code `json` result** carries `result`, `session_id`, `total_cost_usd`, `usage`, `modelUsage` per model (`costUSD`, `inputTokens`, `outputTokens`, `cacheReadInputTokens`, `cacheCreationInputTokens`, `costBasis`), `num_turns`, `duration_ms`, `duration_api_ms`, `permission_denials`; `stream-json` adds `system/init` (model, tools, `plugins`, `plugin_errors`, `mcp_servers`, `mcp_server_errors`, `capabilities`) and `system/api_retry` (`attempt`, `max_retries`, `error_status`, `error` category). The docs describe failing CI on a non-empty `plugin_errors` or `mcp_server_errors`. (headless "Get structured output", "Read session metadata"; agent-sdk/cost-tracking.) [verified]
14. **Claude Code `--bare`** skips discovery of hooks, skills, commands, subagents, plugins, MCP servers, auto memory and CLAUDE.md, never reads OAuth credentials (needs `ANTHROPIC_API_KEY` or `apiKeyHelper`), and "will become the default for `-p` in a future release". Without it, "a `-p` session runs the hooks in a project's `.claude/settings.json` and connects the servers in its `.mcp.json`, even in a folder you've never trusted" with "no workspace trust dialog". (headless "Start faster with bare mode".) [verified]
15. **Codex**: `codex exec "<prompt>"` streams progress to stderr and prints the final message to stdout; `--json` switches stdout to JSONL with `thread.started`, `turn.started|completed|failed`, `item.started|completed` (items: agent messages, reasoning, command executions, file changes, MCP tool calls, web searches, plan updates) and `error`; `-o/--output-last-message <path>`; `--output-schema <file>`; `--ephemeral` (no rollout file); `--skip-git-repo-check`; `--ignore-user-config`; `--ignore-rules`; `--strict-config`; `-c key=value` overrides; `codex exec resume [SESSION_ID]` or `--last`; `codex exec review`. (https://learn.chatgpt.com/docs/non-interactive-mode; `codex-rs/exec/src/cli.rs` lines 18-85, 188-253.) [verified]
16. **Codex exit codes and bounds**: the non-interactive page "does not explicitly specify turn limits, time limits, or exit codes"; the config reference has no key bounding turns, time or cost per run; source exits 1 on configuration and bootstrap failures (`codex-rs/exec/src/lib.rs` lines 355, 373, 650, 660, 1015, 1395). ### 4. Extension mechanisms

27. **pi**: TypeScript extensions loaded from `.pi/extensions`, `~/.pi/agent`, packages, or `-e <path|npm:|git:>`. Events include `before_agent_start` (edit prompt sections, selected tools, or force the system prompt), `tool_call` ("can mutate input or block execution"), `tool_result` (composing transforms), `message_end` (replace a finalized message), `context`/`context_with_system`, `turn_end` and `agent_before_settle` (may return `continue: true` for one more model request), `provider_stream_event` (read-only), `cache_warming_decision`, `user_bash`, plus session and resource-discovery events. Extensions register custom tools (TypeBox schema, `execute()`), MCP servers via `builtin:mcp` and `.pi/mcp.json`, and CLI flags. Skills follow the Agent Skills specification at `.pi/skills`, `.agents/skills` and `~/.agents/skills` (and `/skill:name` commands); `.claude/skills` is not listed. `AGENTS.md` and `CLAUDE.md` load as context regardless of project trust; `-nc` disables that. Pi packages bundle extensions, skills, prompt templates and themes from npm, git or a local path. (`extensions.md` lines 95-170; `skills.md` lines 7-63; `security.md` "Understand project trust"; `packages.md`; `cli.md` "Resources".) [verified]
28. **Claude Code**: hooks on 33 events with five handler types (`command`, `http`, `mcp_tool`, `prompt`, `agent`). `PreToolUse` can block, rewrite `updatedInput`, inject `additionalContext` and return `permissionDecision: allow|deny|ask|defer`; `PermissionRequest` returns `decision.behavior`; `PostToolUse` can replace `updatedToolOutput`; `Stop`/`SubagentStop` can block completion; `UserPromptSubmit`, `SessionStart`, `PreCompact`, `PostCompact`, `SessionEnd`, `WorktreeCreate|Remove`, `TaskCreated|Completed`, `PreModelSwitch`, `ConfigChange`, `Elicitation`, `Notification`, `Setup` and others. Hooks cannot intercept `EndConversation`, direct reads of `AGENTS.md` (only CLAUDE.md imports fire `InstructionsLoaded`), prompt-cache behaviour, or MCP init errors. Exit code 2 blocks. Configured in user/project/local settings, plugin `hooks/hooks.json`, skill/agent frontmatter, managed policy. Skills live in `.claude/skills`; plugins via `--plugin-dir`/`--plugin-url`; subagents via `--agents` JSON or `.claude/agents`; MCP via `--mcp-config` with `--strict-mcp-config`. (https://code.claude.com/docs/en/hooks; cli-reference.) [verified]
29. **Codex**: `AGENTS.md` (bounded by `project_doc_max_bytes`); skills discovered from `.agents/skills` up to the repo root, `~/.agents/skills`, `/etc/codex/skills` and bundled; `SKILL.md` with `name` and `description`, invoked by `$skill` or implicitly; "build on the open agent skills standard" (https://learn.chatgpt.com/docs/build-skills); `.claude/skills` is not a discovery path. Hooks: `PreToolUse` (block, rewrite input, inject), `PermissionRequest` (block), `PostToolUse` (feedback, inject), `PreCompact`, `PostCompact`, `SessionStart` (block, inject), `SessionEnd`, `SubagentStart|Stop`, `UserPromptSubmit`, `Stop` (continuation), `Interrupt`; configured in `~/.codex/hooks.json` or `[hooks]` in `config.toml`, repo `.codex/hooks.json`, plugin hooks, or `requirements.toml`; enabled by default, `[features] hooks = false` disables. "The documentation does not mention `codex exec` compatibility with hooks." MCP via `mcp_servers` (`command`/`url`, `required`, timeouts); plugins bundle skills, MCP servers and hooks via marketplaces, installed with `/plugins`; `execpolicy` `.rules`; `notify` command. (config-reference; hooks; plugins.) [verified; hooks-in-exec unverified]
30. **OpenCode**: plugins are JS/TS modules in `.opencode/plugins/`, `~/.config/opencode/plugins/` or npm (`"plugin": [...]`, installed by Bun). Hook names: `tool.execute.before` (can block or alter arguments), `tool.execute.after`, `permission.asked`, `permission.replied`, `chat`/`message.*`, `session.created|compacted|deleted|diff|error|idle|status|updated`, `file.edited`, `command.executed`, `shell.env`, `lsp.*`, `tui.*`, `experimental.session.compacting`; plugins add custom tools with `tool({description, args, execute})`. Agents are Markdown with frontmatter (`description`, `mode`, `model`, `temperature`, `prompt`, `permission`, `steps`, `hidden`) in `.opencode/agents/` or `opencode.json`. ## What others do

- **JSONL event streams, not single JSON blobs, are the common headless contract.** pi, Claude Code `stream-json`, Codex `--json`, OpenCode `--format json`, Goose `stream-json` and Hermes `--format stream-json` all emit newline-delimited events (7, 9, 11, 15, 17, 18, 19). Only Claude Code also offers a single `json` result object with totals (13); only pi documents the back-pressure hazard of a slow reader (9).
- **Exit status is a weak success signal everywhere.** pi's JSON mode exits 0 on a failed response, pi's print mode exits 0 with empty output on exhausted output budget, Codex and OpenCode do not document exit codes, Goose documents none (8, 16, 17, 18, 51). Harnesses expect callers to inspect the event stream.
- **Run bounds are rare.** Only Claude Code (`--max-turns`, `--max-budget-usd`) and Goose (`--max-turns`) bound a run from the CLI; pi, Codex and OpenCode leave this to the caller (10, 12, 16, 17, 18).
- **Cost is client-side estimation from a price table.** Claude Code says so explicitly; OpenCode and pi price via models.dev-style tables and have open issues about wrong or missing prices; Codex reports tokens only (33 to 36, 54).
- **The Agent Skills specification is converging.** pi, Codex, OpenCode, Goose and Hermes all reference agentskills.io or `.agents/skills`; OpenCode and Goose additionally read `.claude/skills` for compatibility; Codex and pi do not (27, 29, 30, 31, 32).
- **Pre-tool-call interception exists in four harnesses** (pi `tool_call`, Claude Code `PreToolUse`, Codex `PreToolUse`, OpenCode `tool.execute.before`), with block and rewrite semantics; Goose and Hermes gate only shell commands (27 to 31, 49, 50).
- **Isolation is delegated to the operating system or a container, and shell-only where built in.** Claude Code's sandbox and Codex's sandbox wrap shell commands; pi has none and tells you to use a container; Hermes skips its own checks inside containers (45 to 50).
- **Unattended runs need an explicit "nobody will answer" switch:** Claude Code `--permission-prompts none`/`dontAsk`, Codex "fail rather than prompt", OpenCode `--auto`, Hermes `single_query_mode: deny` (46, 47, 48, 50).
- **Sessions are first-class and resumable by id in every candidate**, with pi and Claude Code also accepting caller-chosen ids (39 to 44).
- **Vendor harnesses are vendor-locked on models; community harnesses are provider-agnostic.** Claude Code is Claude-only, Codex is Responses-API-only, Gemini CLI is Gemini-only; pi, OpenCode, Goose and Hermes plug in many providers (21, 23, 24, 25, 26, 58).
- **Projects move organisations.** Three of six candidates changed GitHub homes recently (pi-mono to earendil-works/pi, sst to anomalyco, block to aaif-goose) (1, 4, 5).
- **The predecessor's headless pain points are documented harness behaviour, not bugs it imagined:** the 10-minute background wait ceiling and fallback-model-does-not-cover-quota are both in current Claude Code docs and in an open issue (12, 52, 60, 61).

## Open questions for the thinking run

1. **Is "open source" a hard or soft criterion for the orchestrating harness?** Claude Code fails it (2) while being the only candidate with built-in turn and dollar caps (12) and the richest hook surface (28). Options: treat Claude Code as a model-specific worker invoked by an open-source orchestrator; drop it entirely; relax the criterion. Bears on: 2, 12, 28, 46, 59 to 61.
2. **How much of model-agnostic is needed in practice?** R7.Q5 fixes Anthropic and OpenAI. Codex covers OpenAI and Responses-compatible endpoints only (23); pi, OpenCode, Goose and Hermes cover both vendors (20, 24, 25, 26). If "Anthropic via subscription" matters, OpenCode documents Claude Pro/Max OAuth "with limitations" (24), pi documents a Claude Pro/Max token path under Docker Sandboxes (`containerization.md` heading, not read in depth). Options: require both vendors natively; accept one vendor per harness and route by stage.
3. **Who bounds a run?** Only Claude Code and Goose have CLI bounds (12, 18). Options: pick a harness with bounds; wrap any harness in a supervisor that enforces time/cost from the event stream (pi's per-message `cost` and Claude's `total_cost_usd` make this feasible, 13, 33); accept per-agent `steps` in OpenCode (17).
4. **Can the chosen harness's exit status be trusted, or must the dispatcher parse events?** Evidence says parse events (8, 16, 17, 51). This affects the completeness principle's "error they cannot ignore" (process-spec 6.4).
5. **Which permission posture for unattended workers on the laptop?** pi offers none and expects a container (45); Codex offers an OS sandbox that "fails rather than prompts" (47); Claude Code offers `dontAsk`/`--permission-prompts none` plus an off-by-default Bash sandbox (46); OpenCode offers rule-based allow/deny without isolation (48). Options: containerise every worker regardless of harness; rely on harness-native sandboxing; rule-based permissions only.
6. **Cost accounting source of truth.** Every harness estimates client-side (34, 36) and two have open issues about wrong prices (52, 54). Options: trust harness totals; reconcile against provider usage APIs; count tokens only and price in our own table.
7. **Telegram grilling bot: harness-native gateway or our own long-poller?** Hermes ships a Telegram gateway and cron (32) but is general-purpose (57); every other candidate needs our poller plus `--resume`/`--session-id` (39 to 44). Agent 4's file covers orchestration; this file only establishes that all candidates can resume by id from the CLI.
8. **Skill and guidance-file compatibility across harnesses.** If panelator keeps `.claude/skills` for interactive Claude Code, OpenCode and Goose read them and pi/Codex do not (27, 29, 30, 31); `.agents/skills` is read by pi, Codex, OpenCode and Goose (27, 29, 30, 31) but not by Claude Code (28, not listed). Options: author skills under `.agents/skills` and symlink; maintain two trees; choose one harness.
9. **Does Codex's hook system apply to `codex exec`?** Not stated (29). Needed before Codex could host a review stage with a PreToolUse guard.
10. **Hermes's suitability as a coding harness** is untested here (57) and its issue tracker unread (56). Options: include in hands-on; defer.
11. **Project stability risk.** Three candidates moved orgs within the year and pi auto-closes new-contributor issues (1, 4, 5). Whether that matters for a multi-year repo is a judgment call.

## Recommended hands-on task and measurements

Run the same task, verbatim, through each surviving harness (pi, OpenCode, Goose, Hermes; Codex with OpenAI only as a control; Claude Code headless with Anthropic only as a second control), twice per harness where it supports both vendors: once on an Anthropic model and once on an OpenAI model of comparable tier, chosen by a model flag alone with no other change.

**Task** (self-contained, product-relevant, verifiable, exercises shell, edits, tests and git; it implements process-spec 6.4 which panelator needs anyway):

> In this repository, create `tools/gh-list/` as a small Node script with tests. `gh-list issues --repo <owner/name> --author <login>` must list all open issues by that author using the GitHub REST API with full pagination, assert the number collected equals the server-reported total (use the search endpoint's `total_count` or the `Link` header last page), print one JSON line per issue to stdout, and exit non-zero with a clear message on stderr if the count does not match or any page fails. Add a vitest suite that mocks the HTTP layer to cover: one page, three pages, a truncated final page, and a failed middle page. Run the tests, make them pass, and commit on a branch named `hands-on/<harness>-<vendor>` with a conventional commit message. Do not push.

Provide every harness the same `AGENTS.md` (two paragraphs: repo layout, "run `pnpm test` before claiming done") and nothing else; no skills, no MCP. Run from a fresh worktree per attempt, unattended, with the harness's documented "nobody will answer" setting (Findings 45 to 50), under a 30-minute process timeout.

**Measurements per attempt** (record in a CSV alongside the raw event stream):

1. Outcome: tests pass on a clean `pnpm test` run by the evaluator; branch and commit exist; diff limited to `tools/gh-list/` and lockfile.
2. Wall-clock seconds to exit; number of model turns and tool calls (from events).
3. Tokens in/out/cache-read/cache-write and harness-reported USD, then the same from the vendor's usage dashboard for the time window, and the ratio (Findings 33 to 38, 6).
4. Exit code versus actual outcome, including one deliberately failing run (invalid API key) to see whether the exit code reflects it (Findings 8, 16, 17).
5. Permission stalls: did the run ever block waiting for a human; did it hang past its own idle ceiling (Findings 12, 53).
6. Resume: after the first attempt, send a follow-up ("also add `--state all`") by session id from a different shell; record whether context carried over and the extra cost (Findings 39 to 44). This is the Telegram grilling-bot proxy.

9. Cleanliness: stray processes after exit, files written outside the worktree, session files left behind (Findings 45 to 50).
